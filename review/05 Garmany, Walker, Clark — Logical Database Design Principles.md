## 3. Кандидаты дополнений

**К-11. Методическое сопровождение денормализации (к LDM-032 / прил. С; без изменения модальности).**
Материал для раздела «обоснованная избыточность»: (а) критерий выбора — волатильность: избыточность концентрируется на редко изменяемых данных, для волатильных — оценка цены поддержки; (б) приёмы с обязательным правилом согласованности: сводная колонка + механизм синхронизации (триггер/процесс, включая события сброса); pre-aggregation для частых агрегирующих запросов; (в) pre-joining/materialized view как альтернатива структурной денормализации (выровненное представление без изменения структуры); (г) для чисто читаемых аналитических хранилищ — риск рассинхронизации ниже (профиль нагрузки).
Основание: «Generally speaking, you are better off concentrating denormalization on nonvolatile fields (those that are updated infrequently)»; «One of the best ways to keep this field in sync is to create a trigger on the order_detail table that fires when records are inserted, updated, or deleted»; «The snapshot is used to create a flattened view of the required data without actually denormalizing the underlying table structure» (гл. 5).

**К-12. Состав чек-листа требований этапа (к 5.10 / Ж.3, методическое).**
Пять рубрик проверки требований: входы (что запускает процесс), выходы (результаты; выход одного процесса — вход другого), процессы (действия), измеримые характеристики (производительность/носители), контроль (проверки и ограничения доступа). Использование: критерий «дизайн завершён» сверяется с чек-листом.
Основание: «A system requirements checklist should include *inputs*, *outputs*, *processes*, *performance,* and *controls*… you can use the checklist to determine when a database design is completed and that it meets agreed-upon criteria» (гл. 1).

**П-10. Многозначный атрибут → ассоциативная сущность (прил. Р).**
Многозначный атрибут в реляционной форме разрушает уникальность записи и ведёт к составному ключу с избыточностью; разрешение — отдельная сущность ассоциации с наследованным ключом. Пример Hobby → «Hobby Listing» (SSN + Hobby #).
Основание: «multiple values for a single attribute indicate the need for another entity class» (гл. 2, Set-Valued Attributes); рис. 2.4 «Associative (weak) entity».

**Методические заметки:** «subtype constraint» как синоним критерия принадлежности (CDM-027/T-031) — рабочий термин для прил. Р; выбор формы ERD (овалы/блок) по фазе работы — заметка для прил. В; три способа идентификации объекта — иллюстрация к 2.6; VARRAY/nested table — формы выражения многозначности для ОР-профиля (прил. Б); Kimball-гранулярность и ключи — справка для аналитического профиля (прил. Б).

**Термины:** новых терминов в словарь не вводится («lookup table» покрывается справочными данными LDM-033; «subtype constraint» — дубль T-031).

## 4. Конфликты и осознанные ограничения

- **Конфликтов обязательств: не выявлено.**
- **Терминологические неточности источника (не принимаются):** «A weak entity class is one that has no values of its own» — определение слабой сущности неверно относительно канона (слабая сущность зависит в идентификации/существовании); канон Правил — CDM-019/T-022. «Шесть уровней нормализации» — счёт условен (1NF…5NF + DKNF). В материалах серии цитировать с оговоркой.
- **Различие областей (не конфликт):** рекомендация «ограничения — после стабилизации модели, только универсальные» относится к декларативным ограничениям СУБД и не ослабляет CDM-025 (документирование бизнес-правил обязательно с самого начала); запрет производных данных в 3NF — про нормализованную структуру, не отменяет LDM-024 (производные атрибуты в модели при бизнес-значимости).
- **Вне охвата (осознанные):** SQL DDL/DML и листинги Oracle (реализация); реляционная алгебра; репликация; OLTP-производительность, блокировки, индексы; хранилища данных (гл. 8–10) — ФМД/физика вне границ 1.5; методы OOA/UML (гл. 6) — свой перечень у прил. В.
