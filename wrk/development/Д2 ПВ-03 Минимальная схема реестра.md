# Д2 ПВ-03: минимальная схема реестра требований (материалы)

**Версия:** 0.1, 2026-10-11.
**Статус:** рабочие материалы этапа Д2 (план 0.4, § 4); подготовлены инициатором работ инициативно. Решением пользователя от 2026-10-11 утверждение ведётся **одним пакетом** (схема + правила переноса ПВ-13 + формат) после прогона контура R; до утверждения Д3 не разблокирован.
**Назначение:** минимальная схема реестра требований и связанных записей (ПВ-03) по прил. А С01 v0.8 — в машиночитаемой форме (JSON Schema draft 2020-12, носитель YAML), с испытаниями на трёх типах норм (план § 6 п. 4) и отрицательными примерами (критерий ПВ-03 плана § 3).
**Основание:** план 0.4 — § 3 (ПВ-03, ПВ-13), § 4 (Д2), § 6 п. 4, § 9; С01 v0.8 — 1.8, 3.5–3.11, 4.2–4.3, 10.1, прил. А; реестр источников (trash/ № 22–25, 28); Проба переноса v0.1 (Р-004); реестр решений — Р-011.
**Связанные решения:** Р-004 (таблицы Б2/Б5, проба Б1–Б5); решения пользователя 2026-10-11 (формат YAML; порядок утверждения пакетом).

## 0. Принятые рабочие решения (входят в утверждаемый пакет)

### 0.1. Формат реестра — YAML (решение пользователя, 2026-10-11)

Отклоняет техническую рекомендацию плана § 9 («JSON для структурированных записей»). Оценка по явным критериям § 9:

| Критерий § 9 | Оценка для YAML |
|---|---|
| Наличие валидатора схемы | выполнено: JSON Schema draft 2020-12, проверка `tools/registry_check.py` (PyYAML + jsonschema); схемы тоже ведутся в YAML — единая форма |
| Читаемость diff при ревью | выполнено: записи одноуровневые, порядок полей фиксируется шаблоном; diff по строкам |
| Комментарии для рецензентов | выполнено: комментарии `#` в схемах и записях — прямой довод выбора (у JSON отсутствует) |
| Совместимость со средой хранения модели (ПВ-10) | нейтрально: YAML читается всеми средствами; выбор среды хранения авторитетной модели — Д4, не предрешается |
| Объём ручного ввода | умеренно: записи компактнее JSON; чувствительность к отступам — принятый риск, компенсируется валидатором и каноническим стилем (README реестра) |

Текст формулировок внутри записей — без markdown-разметки (плоские строки, `>-`); документная часть правил — Markdown, как и прежде.

### 0.2. Прочие решения

- Схемы хранятся в реестре вместе с записями (`wrk/standard/registry/schema/`), версия схем — в манифесте выпуска (прил. А: «фиксирует версии всех компонентов, включая версию схемы реестра»).
- Иллюстративные значения С01 (M-042, EV-0451, PR-009) в испытательных примерах заменены собственными; записи примеров помечены испытательными — реального переноса требований нет до Д3.
- Таблица переноса (прил. Ф) будет вестись в `wrk/standard/appendices/` (план § 9); каталог создан, наполнение — Д3.

## 2. Однозначность правил (критерий закрытия ПВ-03)

| Правило прил. А | Как закодировано | Отрицательный пример |
|---|---|---|
| «применимость не определена» — только для черновика | условие: ось содержит `undefined` → `status: draft` | `req-approved-undefined.yaml` |
| `undefined` — отдельное значение, не смешивается с конкретными | условие: ось с `undefined` → `maxItems: 1` | `req-mixed-undefined.yaml` |
| пустой список оси не используется | `minItems: 1` на каждой оси | `req-empty-axis.yaml` |
| `stage` — только классификатор 4.2 (1–8) | целые 1–8; этапы 1–6 исходников и Д0–Д8 невалидны | `req-stage-out-of-range.yaml` |
| модальность — закрытый перечень кодов 3.6/Б5 | `enum` (required/forbidden/recommended/allowed) | `req-bad-modality.yaml` |
| `replaces` для режимных связей не применяется | типа связи нет в `enum` матрицы | `asis-replaces.yaml` |
| при `unchanged` ссылка на адаптированное требование отсутствует | условие `way: unchanged` → `linked` запрещён | `asis-unchanged-with-link.yaml` |
| результаты проверки — закрытый перечень | `enum` (verified/failed/not_applicable/not_checked/insufficient) | `verification-bad-result.yaml` |
| `adapts_for_mode` → отдельный ID + обоснование | условие `way: adapted` → `linked`, `rationale` обязательны; `not_applied` → `rationale` обязательно, связей нет | покрытие тестами `test_adapted_requires_link_and_rationale`, `test_not_applied_requires_rationale` |
| `procedure` записи проверки до наполнения прил. Ж (Д7) | `null` допускается (решение REV-002/std-002); поле присутствует обязательно | покрытие тестом `test_verification_procedure_nullable` |

Смешанный режим (прил. А): применимость определяется по состоянию фрагмента — ось `mode` в записи требования; `mixed` как значение оси не используется (модель в целом не характеризуется). Семантика отражена в README реестра и переносится в текст правил при наполнении разд. 3 (редакция 0.1-д1, 3.5).

## 3. Испытания схемы (план § 6 п. 4: атомизация на трёх типах норм)

### 3.1. Положительные примеры

| Пример | Тип нормы (план § 6 п. 4) | Что демонстрирует |
|---|---|---|
| `requirement-cdm-001.yaml` | паспортное требование | четырёхчастная норма «состав полей одного документа не дробится» (С01 3.10): десять реквизитов паспорта — одна атомарная запись; критерий проверки по реквизитам |
| `requirement-ldm-034.yaml` | условная норма | условная применимость необязательных конструкций — в `conditions`, не в модальность (Б5, прим. 2); отсутствие конструкций ≠ невыполнение |
| `requirement-cdm-015.yaml` | норма с допустимой неизвестностью | формулировка по образцу С01 3.10 (Проба 3.3): выполнима при неизвестной кардинальности — предметный факт отделён от обязанности документирования |
| `requirement-ldm-031.yaml` + `requirement-ldm-039-adapted.yaml` | двух-ID случай (Б1, правая ветвь) | различие обязательств по режимам → `mode: [to-be]` и `mode: [as-is]`, разные `stage` (6/5); ID LDM-039 — условный, назначается на Д3 |
| `asis-application-*.yaml` (3 шт.) | матрица применения | все три способа: `unchanged`/`applies_as_is` (×2, с расширенным критерием AS-IS без изменения обязательства) и `adapted`/`adapts_for_mode` со ссылкой и обоснованием |
| `standard-release-0.2.yaml` | манифест выпуска (draft) | состав: требования с редакциями + компоненты с версиями, включая `schema` |
| `verification-v000123.yaml` | запись результата | `insufficient` — недостаточность сведений о модели ≠ неопределённость правила применимости (прил. А) |

### 3.2. Отрицательные примеры — см. § 2 (8 файлов; каждый отвергается по целевому правилу). Дополнительные правила (not_applied → rationale; procedure: null) покрыты юнит-тестами: новые файлы в кандидате прогона std-002 невозможны (манифест базы фиксирует состав), эквивалентное покрытие — `tests/test_registry_check.py` (решения REV-001/REV-002).

### 3.3. Прогон

- `python3 tools/registry_check.py selftest` — 18 файлов (10 положительных, 8 отрицательных), нарушений согласованности: 0.
- `python3 -m unittest discover -s tests` — 54 теста OK (43 прежних по review.py + 11 `tests/test_registry_check.py`, включая покрытия решений REV-001/REV-002 прогона std-002), 2 пропуска (прежние).
- Запуск воспроизводится также как `uv run --with jsonschema python -m unittest discover -s tests` (зависимости: pyyaml, jsonschema≥4.10).
