# Приложение А. Каталог требований и схема связанных записей проверки

**Версия:** 0.3-в1 (волна 1 Д7, рабочая редакция стандарта 0.3). Статус — рабочий документ в составе рабочей редакции; утверждение — по порядку плана разработки (ПВ-01).

## А.1. Назначение и состав

Приложение А — машиночитаемый каталог требований стандарта и связанных записей проверки (3.11). Каталог является **мастер-источником** нормативных формулировок: текст стандарта проходит автоматическую проверку консистентности с ним; две независимо редактируемые копии нормативной формулировки не допускаются.

Состав каталога (реестра):

| Компонент реестра | Содержание | Схема |
|---|---|---|
| Требования | Стабильные ID, редакции, формулировки, модальность, применимость, критерии выполнения, связи | `requirement.schema.yaml` **1.1** |
| Применение AS-IS | Матрица применения требований регламента AS-IS (строки) | `asis-application.schema.yaml` |
| Выпуски | Манифесты выпусков (требований и стандарта) | `standard-release.schema.yaml` |
| Результаты проверки | Записи результатов проверки соответствия | `verification.schema.yaml` |

Расположение: `wrk/standard/registry/` (правила ведения — `registry/README.md`). Проверки согласованности: `python3 tools/registry_check.py check|selftest`; тесты — `uv run --with jsonschema python -m unittest discover -s tests`.

Текущее состояние каталога: выпуск требований **0.2-д3** (35 записей, approved; манифест — `releases/release-0.2-д3.yaml`), матрица применения AS-IS — 33 строки пилотного среза (полная матрица — с регламентом AS-IS, волна 4 Д7).

## А.2. Идентификация требований

Префиксы: `GEN-xxx` — общие требования; `CDM-xxx` — требования к КМД; `LDM-xxx` — требования к ЛМД. Правила жизненного цикла идентификатора — 3.9: перенос без изменения обязательства сохраняет ID; редакционная правка меняет редакцию записи; разделение/объединение — новые ID со связями `replaces`/`refines`; выведенные из действия ID повторно не используются. Прослеживаемость к исходным документам — прил. Ф.

## А.3. Коды модальности (3.6)

| Код | Модальность | Ключевое слово |
|---|---|---|
| `required` | предписание | «должен», «обязательно» |
| `forbidden` | запрет | «не допускается» |
| `recommended` | рекомендация | «рекомендуется» |
| `allowed` | разрешение | «допускается» |

Модальность выражает характер требования, а не степень важности. Предписания и запреты образуют множество обязательных требований.

## А.4. Запись требования

Структурированное представление требования (иллюстративный пример; фактические записи — в реестре):

```yaml
schema_version: 1
id: LDM-017
revision: 2                      # редакция требования (3.9)
formulation: >-                  # дословная формулировка (мастер-источник)
  …
modality: required               # required | forbidden | recommended | allowed
applies_to:                      # критерии применимости (3.5)
  level: [LDM]
  profile: […]
  mode: [to-be, as-is]
  stage: [5]                     # классификатор этапов 4.2
conditions: []                   # условия, не выражаемые осями
exception_allowed: true          # связь с 3.8
verify:
  kind: structural               # вид проверки из 10.1
  criterion: "…"
  procedure: null                # контрольная процедура (прил. Ж)
  evidence: []                   # ожидаемые ТИПЫ свидетельств (прил. Г)
sources: []                      # перенос из исходных документов (прил. Ф)
based_on: []                     # нормативные основания (1.7)
relations:
  depends_on: []
  refines: []
  replaces: null                 # список — при объединении (схема 1.1)
status: draft                    # draft | approved | withdrawn
```

## А.5. Семантика применимости

- Отсутствие оси или условия применимости — «применимо ко всем» значениям оси.
- «Применимость не определена» — отдельное явное значение, **допускается только для черновой записи** (`status: draft`); в утверждённый выпуск требования с неопределённой применимостью не включаются.
- Если при проверке конкретной модели применимость установить невозможно, вопрос регистрируется (4.8) и разрешается до положительного заключения по соответствующему обязательному требованию.
- Различаются: неопределённость правила применимости (устраняется владельцем требования) и недостаточность сведений о проверяемой модели (результат `insufficient`).
- Несколько значений одной оси — любое из них (дизъюнкция); несколько осей — одновременное выполнение (конъюнкция). Пустой список значений оси не используется; условия, не выражаемые осями, задаются полем `conditions`.
- Ось `stage` задаёт этап, к завершению которого требование должно быть выполнено; требование сохраняет применимость при последующей проверке, приёмке и сопровождении результата этапа; нумерация этапов не устанавливает обязательную хронологию (4.3).
- Смешанный режим (3.3): применимость определяется отдельно для AS-IS- и TO-BE-фрагментов по их состоянию (5.7); значение `mixed` у модели не означает неприменимость требований; дополнительно применяются требования к разграничению состояний (3.4) и переходным соответствиям. Ось `mode` характеризует состояние фрагмента, а не режим работы в целом.

## А.6. Манифесты выпусков

Манифест фиксирует согласованный набор требований и сопутствующих материалов выпуска, а не текущее состояние реестра; редакция требования может входить в несколько последовательных выпусков. Манифест содержит версии всех компонентов, влияющих на содержание, применимость, проверку и согласование выпуска, включая версию схемы реестра, — это обеспечивает воспроизводимость проверки по прошествии времени.

```yaml
schema_version: 1
record: standard_release
release: "0.2-д3"
date: "ГГГГ-ММ-ДД"
status: draft                    # draft | approved
includes:
  requirements: [{id: GEN-001, revision: 1}, …]
  components:                    # все компоненты, влияющие на данный выпуск
    - {ref: schema, version: "…"}
    - {ref: "прил. Г", version: "…"}     # минимальные метаданные
    - {ref: "прил. И", version: "…"}     # классификация ИОД
    - {ref: "прил. К", version: "…"}     # матрица ответственности
    - {ref: "прил. Ж", version: "…"}     # контрольные процедуры
    - {ref: "глоссарий", version: "…"}
    - {ref: "прил. Б", version: "…"}     # профили моделирования
```

Действующие манифесты — `releases/` реестра. Манифест выпуска регламента AS-IS ссылается на выпуск стандарта (1.8); применение рассогласованных выпусков не допускается.

## А.7. Матрица применения требований AS-IS

В составе регламента AS-IS (1.8); схема записи — `asis-application.schema.yaml`. Для каждого требования заявленного выпуска фиксируются: способ применения (`unchanged` / `adapted` / `not_applied`), ссылка на адаптированное либо специальное требование AS-IS, обоснование различия и критерий проверки в AS-IS. Типы связей: `applies_as_is` — одинаковое обязательство, один идентификатор; `adapts_for_mode` — различающиеся обязательства, отдельные идентификаторы; `replaces` для режимных связей не применяется. Матрица устанавливает применение норм, а не результаты проверки; полная матрица — волна 4 Д7.

## А.8. Запись результата проверки соответствия

Требование определяет, *как проверять*; запись результата — *что установлено* для конкретной модели. Записи хранятся отдельно от требований.

```yaml
schema_version: 1
record: verification
id: V-000123                     # идентификатор записи (запуска) проверки
requirement: {id: LDM-017, revision: 2}
standard_release: "0.2-д3"       # проверенный набор требований (манифест)
procedure: null                  # контрольная процедура (прил. Ж), при наличии
scope: model                     # model | fragment
object: {model: M-042, version: 5}   # версия модели либо фрагмент; тестовые копии — из пространства имён тестовых артефактов (12.2)
result: verified                 # verified | failed | not_applicable | not_checked | insufficient
evidence: [EV-0451]              # ссылки на конкретные свидетельства (прил. Г)
checked_by:
  initiator: "…"                 # инициатор запуска (роль/исполнитель)
  executor: "…"                  # исполнитель; для автоматической процедуры — средство/система
  date: "ГГГГ-ММ-ДД"
exception: null                  # исключение (3.8) при наличии
```

«Не проверено» (`not_checked`) не считается ни выполнением, ни допустимым исключением; «недостаточно сведений» (`insufficient`) требует доопределения; связь результатов с решением о приёмке — 10.11.

## А.9. Различение объектов проверки

Записи соответствия требованиям стандарта (настоящее приложение) и свидетельства (прил. Г) — разные объекты (10.1, GEN-004). Свидетельства связываются с объектом подтверждения: утверждением, бизнес-правилом, элементом модели, процедурой или фактом выполнения организационного требования. Помимо бизнес-правил свидетельствами являются, например: протокол утверждения, результат проверки обязательных метаданных, отчёт о целостности идентификаторов, манифест выпуска, результат сравнения экспорта с моделью. Записи проверки ссылаются на свидетельства при необходимости.

## А.10. Правила ведения

- Реестр — мастер-источник формулировок (3.11); текст стандарта формируется из реестра либо проходит автоматическую проверку консистентности (контроль дословности по ID + revision — план разработки § 9).
- Крупные изменяемые каталоги допускается вести как управляемые реестры со ссылками из текста стандарта; для внешних реестров указываются версия, владелец и порядок включения изменений в действие.
- Идентификаторы и решения не переиспользуются; история изменений сохраняется (3.9).
