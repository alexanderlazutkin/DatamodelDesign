# Локальные помощники (контур R и реестр требований)

## tools/review.py — помощник рецензирования (контур R)

`tools/review.py` — реализация шага А2 плана «План-инструкция по автоматизации
рецензирования». Только стандартная библиотека Python (3.10+). Без LLM API,
сети, базы данных, сервера, Git-мутаций и произвольного shell.

Помощник: фиксирует входы (неизменяемый снимок + SHA-256-манифест), выполняет
формальные проверки (схемы, ID, ссылки, цитаты, allowlist, предел раундов),
записывает явно переданные решения человека, строит diff кандидата и сводку.

Помощник НЕ: не утверждает содержание, не применяет кандидат к рабочим файлам,
не выполняет commit/push, не заменяет решений человека, не считает мнение LLM
утверждением. **Код возврата 0 — формальная операция выполнена, не одобрение.**

## Команды

```bash
uv run python tools/review.py <команда> [параметры]   # --help для каждой команды
```

| Команда | Назначение |
|---|---|
| `prepare --task <task.json> --run <id>` | создать запуск: снимок, манифест, журнал (существующий run-id не перезаписывается) |
| `check --run <id> --target snapshot` | проверить неизменность базы (хеши снимка vs манифест) |
| `record-review --run <id> --round N [--phase review\|verification] --file <отчёт.json>` | принять отчёт рецензента после валидации структуры, ссылок и цитат |
| `record-decision --run <id> --round N --file <decisions.json>` | записать решение человека по замечаниям |
| `check --run <id> --target candidate --round N` | проверить кандидат: полный комплект, allowlist, changes.json → зафиксировать манифест кандидата |
| `diff --run <id> --round N` | построить diff кандидата относительно исходного снимка (накопительный) |
| `record-approval --run <id> --round N --file <approval.json>` | записать одобрение/доработку/остановку по конкретному diff |
| `summary --run <id>` | сводка с полной перепроверкой целостности всех артефактов |

Коды выхода: `0` — формальная операция выполнена; `1` — нарушения проверяемого
контракта (печатается с точным местом); `2` — ошибки входов/среды.

## Пошаговый порядок одного запуска

### Что настроить ДО запуска (не кодом, решениями человека)

1. **Объект и охват** — какой документ/фрагмент ревьюится (контур R: текст
   правил). Реальные материалы `src/` — только чтением; проверять снимок.
2. **Модель рецензента** — проектный агент `.opencode/agent/reviewer.md`
   (по умолчанию) или `.opencode/agent/reviewer-alt.md` (альтернативное
   мнение). Смена модели: изменить строку `model:` в файле агента и
   **перезапустить opencode**. Доступные модели Cherry: см.
   `~/.config/opencode/opencode.jsonc` → `provider.cherry.models`
   (gpt-6-astra, deepseek-v4-pro, qwen3.8-max, claude-opus-5.5, glm-5.2).
   Инструкция роли `tools/review-assets/reviewer.md` самодостаточна — рецензента
   можно запустить в любой другой оболочке/модели и передать результат файлом.
3. **Права и среда** — технический read-only средой НЕ обеспечивается.
   Рецензент-субагент работает без пишущих инструментов; целостность входов
   гарантируется сверкой SHA-256 (помощник проверяет её перед каждым шагом).
4. **Предел раундов** — поле `max_rounds` в задании (1–5). Раунд = ревью →
   решения → кандидат → повторная проверка → решение по diff. Исчерпание
   предела → `stopped_with_open_items`, не «одобрено».
5. **Чек-лист** — `tools/review-assets/checklist-standard.json` (версия и
   SHA-256 фиксируются в манифесте; менять между раундами нельзя).

### Альтернативное мнение (reviewer-alt)

`reviewer-alt` — второй агент-рецензент на другой модели (закрепляется в
`.opencode/agent/reviewer-alt.md`, строка `model:`; смена — как у основного,
с перезапуском opencode). Назначение: независимый повторный проход по тому же
чек-листу и той же базе — другое семейство моделей ловит слепые зоны первого
рецензента. Три сценария запуска:

1. **Как рецензент раунда.** Управляющая сессия вызывает субагента
   `reviewer-alt` вместо `reviewer` с теми же параметрами прохода; отчёт
   штатно записывается через `record-review` (валидация полная).
2. **Как параллельное второе мнение.** Вызов на ту же базу до/во время
   принятия решений; отчёт сохраняется как справочный
   (`wrk/tmp/<run>-…-alt.json`) и используется человеком при выборе ID
   замечаний. Помощник его автоматически НЕ записывает: в раунде один слот
   `review.json`, повторная запись другого содержимого — конфликт (код 1).
   Это осознанное ограничение первой версии.
3. **Во внешней оболочке/другой модели.** Новая сессия любого агента +
   инструкция `tools/review-assets/reviewer.md` + параметры прохода
   (run_id, раунд, фаза, base_manifest_hash, пути базы, чек-лист). Результат —
   JSON-файл, далее как в сценарии 2.

Решение о том, считать ли расхождения мнений блокирующим, принимает человек;
`reviewer-alt` не создаёт новых раундов автоматически.

### Порядок шагов

```bash
RUN=demo-001
# 1. Задание: скопировать шаблон wrk/development/review-task-demo-001.json,
#    заполнить inputs / allowed_candidate_paths / max_rounds / roles / environment.
# 2. Создать запуск (снимок + манифест + журнал):
uv run python tools/review.py prepare --task wrk/development/review-task-$RUN.json --run $RUN
uv run python tools/review.py check --run $RUN --target snapshot

# 3. РЕЦЕНЗЕНТ (отдельная сессия, роль reviewer; для повторного мнения — reviewer-alt):
#    запустить агента с инструкцией tools/review-assets/reviewer.md и параметрами:
#    run_id, round, phase=review, base_manifest_hash = sha256(<run>/manifest.json),
#    пути: <run>/manifest.json, <run>/snapshot/, чек-лист.
#    Рецензент возвращает один JSON-отчёт; сохранить в wrk/tmp/…-review.json.
# 4. Принять отчёт (валидация цитат, ссылок, хешей, покрытия чек-листа):
uv run python tools/review.py record-review --run $RUN --round 1 --file wrk/tmp/…-review.json

# 5. ЧЕЛОВЕК, согласование №1: по каждому ID замечания — accept / reject / defer
#    с причиной (нет ответа — нет разрешения). Шаблон решений см. ниже →
uv run python tools/review.py record-decision --run $RUN --round 1 --file wrk/tmp/…-decisions.json

# 6. РЕДАКТОР (основная сессия автора, инструкция tools/review-assets/editor.md):
#    полный комплект файлов в <run>/rounds/01/candidate/, правки только по
#    разрешённым путям и принятым ID; составить changes.json.
# 7. Зафиксировать кандидата и построить diff:
uv run python tools/review.py check --run $RUN --target candidate --round 1
uv run python tools/review.py diff --run $RUN --round 1

# 8. ПОВТОРНОЕ РЕВЮ (фаза verification, база = кандидат): параметры те же,
#    base_manifest_hash = sha256(<run>/rounds/01/candidate-manifest.json);
#    отчёт должен закрыть все принятые замечания (resolution_checks).
uv run python tools/review.py record-review --run $RUN --round 1 --phase verification --file wrk/tmp/…-verification.json

# 9. ЧЕЛОВЕК, согласование №2: увидеть diff (<run>/rounds/01/diff.patch, его
#    sha256), повторный отчёт, остаточные вопросы → approve / revise / stop:
uv run python tools/review.py record-approval --run $RUN --round 1 --file wrk/tmp/…-approval.json

# 10. Сводка (перепроверяет целостность всех артефактов запуска):
uv run python tools/review.py summary --run $RUN
```

Применение одобренного кандидата к рабочим файлам — **отдельная ручная
операция** после сравнения текущих файлов с манифестом; helper её не выполняет.
Коммит/публикация — только по отдельному поручению.

## Каталог запуска (wrk/review-runs/<run-id>/, вне Git)

```
task.json                  зафиксированное задание
manifest.json              состав и SHA-256 базы (снимок, задание, чек-лист)
snapshot/<пути>            неизменяемые входы
events.jsonl               добавляемый журнал событий (seq, время, шаги)
rounds/01/
  review.json              первичное ревью (после валидации)
  decisions.json           решения человека по замечаниям
  candidate/<пути>         редакция-кандидат (полный комплект)
  changes.json             файл → ID принятых замечаний
  candidate-manifest.json  состав и SHA-256 кандидата
  diff.patch, diff.json    накопительный diff к исходной базе + его хеш
  verification.json        повторное ревью кандидата
  approval.json            решение человека по diff
summary.md                 сводка запуска
```

Все ссылки между артефактами — через SHA-256 файлов (проверяется
`sha256sum`). Изменение любого артефакта после записи — обнаруживается
(блокировка перехода или раздел «НАРУШЕНИЯ ЦЕЛОСТНОСТИ» в сводке), хеши не
пересчитываются. Повторная запись того же содержимого безопасна (событие
`idempotent_repeat`); иное содержимое в тот же слот — конфликт (код 1).

## Форматы записей (schema_version 1)

- **Отчёт рецензента** — см. раздел 6 `tools/review-assets/reviewer.md`.
  Правило цитат: цитата сверяется с точностью до переносов строк, пробелов и
  маркеров blockquote (`>`); заявленный диапазон строк должен покрывать место
  цитаты или находиться внутри него. Поле `location.sha256` опционально: если
  указано — обязано совпадать с базой (ловит цитаты из другой версии); если
  опущено — версия файла определяется через `base_manifest_hash` отчёта
  (рекомендуется опускать: LLM ненадёжно копирует длинные хеши).
- **decisions.json**: `decision_maker`, `confirmation_basis`, `decisions[]`
  (`finding_id`, `action`: accept|reject|defer, `reason`), `no_fixes_confirmed`
  (true, если правок нет). Каждый ID отчёта должен иметь решение.
- **changes.json**: `changes[]` (`path` — только изменённые файлы из
  `allowed_candidate_paths`, `finding_ids` — только принятые ID).
  В раунде N > 1 список накопительный: перечисляются ВСЕ файлы, отличающиеся
  от исходного снимка (включая правки прошлых раундов, не тронутые в
  текущем). Для файла, изменённого до текущего раунда, `finding_ids` может
  ссылаться на принятые замечания предыдущих раундов (отложенные и
  отклонённые ID недопустимы); для файла, впервые изменённого в раунде N, —
  только принятые замечания раунда N (правило Р-013).
- **approval.json**: `decision`: approve|revise|stop, `reason`,
  `base_manifest_hash`, `candidate_manifest_hash`, `diff_sha256`,
  `verification_hash`, `residual_findings[]`, `permitted_actions[]`
  (допустимо только `apply_changes`; не исполняется помощником).

## Безопасность и ограничения

- Пути входов: только внутри корня проекта; `..`, абсолютные внешние пути и
  symlinks отклоняются. Помощник пишет только в каталог запуска.
- Текст документов — данные: строки вида «инструкция ассистенту» не
  исполняются (покрыто тестом АТ-11).
- Чтение Git — только две фиксированные read-only команды (`rev-parse`,
  `status`) для полей `base_commit`/`base_commit_dirty`; мутаций нет.
- Технический read-only рецензента средой не обеспечивается — заявляется
  только контроль хешей и отсутствие пишущих инструментов у агента.
- Проверка согласованности текста с мастер-реестром требований отложена до
  Д2–Д3 (АТ-04); контуры P/C (mode ≠ standard_review) — этап А4.
- Локальный JSON-журнал не является электронной подписью и не подтверждает
  личность сам по себе.

## tools/registry_check.py — валидатор записей реестра (Д2, ПВ-03)

Проверяет YAML-записи реестра против схем JSON Schema draft 2020-12 из
`wrk/standard/registry/schema/`. Зависимости: pyyaml, jsonschema (≥ 4.10).
Правила ведения записей и канонический стиль — `wrk/standard/registry/README.md`.

| Команда | Назначение |
|---|---|
| `check --file <запись.yaml> […]` | проверить указанные файлы (тип записи — по полю `record`, иначе требование) |
| `selftest` | испытательный набор: положительные примеры обязаны проходить, отрицательные — отвергаться |

Коды выхода: `0` — формальная проверка пройдена (не утверждение содержания);
`1` — нарушения; `2` — ошибки входов/среды.

## tools/nav.py — навигация комплекта (Р-041)

Вставка block-ID якорей (`^T-xxx`, `^GEN|CDM|LDM-xxx`, `^PR-xxx`), конвертация
плоских отсылок в wikilink Obsidian (первое упоминание в разделе `##`) и проверка
резолва всех ссылок/якорей. Правила — `wrk/standard/Правила оформления и навигации.md`.

```bash
uv run python tools/nav.py anchors   # вставка якорей (идемпотентно)
uv run python tools/nav.py linkify   # плоские отсылки -> wikilink
uv run python tools/nav.py check     # резолв ссылок; код 1 — ошибка приёмки
uv run python tools/nav.py guard     # откат whitespace-артефактов таблиц (Obsidian); код 1 — есть содержательные изменения
```

Ограничения: строки-определения (`^ID`) не линкуются (дословность формулировок);
не линкуются диапазоны, слэш-перечисления, таблицы, код, С01–С09, `Р-xxx`, `Q-*.x`.

## tools/build_docx.py — единый .docx комплекта (Р-041)

Сборка нормативного комплекта в один .docx со сквозной навигацией: титул →
содержание → Правила → Регламент → приложения А…Ф → словарь. Wikilink-цели
получают закладки Word, ссылки становятся внутренними гиперссылками (Ctrl+клик).
Диаграммы ```mermaid отрисовываются в PNG и вставляются картинками (Р-048).

```bash
uv run --with python-docx python tools/build_docx.py --out dist/Комплект_правил.docx
uv run --with python-docx python tools/build_docx.py --verify dist/Комплект_правил.docx
```

Артефакт — `dist/Комплект_правил.docx` **публикуется в Git** (Р-049): пересборка
комплекта сопровождается коммитом артефакта; кэш PNG диаграмм (`wrk/tmp/mermaid-cache/`)
остаётся вне Git. Ошибка сборки (неразрешимая ссылка) — код выхода 1.

Рендер Mermaid (Р-048): mermaid-cli (`npx -y @mermaid-js/mermaid-cli`), Chrome
ищется по `MMDC_CHROME`/`CHROME_PATH`, затем в кэше puppeteer; переопределение
биндари — `MMDC_BIN`. PNG кэшируются по SHA-256 кода диаграммы в
`wrk/tmp/mermaid-cache/` (вне Git) — повторная сборка без перерисовки. При сбое
рендера блок вставляется кодом, в stderr — ПРЕДУПРЕЖДЕНИЕ (код выхода не меняется).
