# Автоматизация рецензирования. Поиск инструмента

> Рабочий документ сессии. Дата: 2026-10-09. Обновляется по ходу сессии.

## Задача

Проработка задачи/документа несколькими LLM-агентами с взаимопроверкой (роли: редактор, ревьюер и т.п.).

## Требования к инструменту

1. Единое рабочее пространство: без ручного перетаскивания файлов между каталогом агента и чатом.
2. Версионность документа в одном месте.
3. Human-in-the-loop: оценка и подтверждение изменений человеком.
4. Настраиваемое число итераций рецензирования между моделями (ролями).
5. Задание/уточнение ролей моделей.
6. Смена провайдеров моделей при необходимости.
7. RAG при рецензировании.
8. Инструмент относительно простой, при необходимости настраиваемый с ИИ-агентом.
9. Кастомизация ролей или создание новых на основе текущих (расширяемость ролевой системы).
9. Использование ролей и скилов

## Кандидаты

### Фреймворки (оркестрация агентов с ролями)

- **CrewAI** — роли (Editor, Reviewer, Writer), последовательные/иерархические пайплайны. Проще всех для старта.
- **AutoGen / AG2** (Microsoft) — диалоги агентов, встроенный pattern `critic` / `reflection`.
- **LangGraph** — граф состояний: цикл «черновик → критика → правка» с контролем числа итераций.
- **OpenAI Agents SDK** — лёгкий вариант: роли задаются системными промптами + handoff.

### Встроенное в IDE / CLI

- **Claude Code / opencode** — субагенты с ролями (`reviewer`, `general`), паттерн VDD/Sarcasmotron: свежий контекст ревьюера, агрессивный ревью, вердикт APPROVED / NEEDS_CHANGES.
- **Cursor / Windsurf** — кастомные агенты-роли в правилах.
- **GitHub Copilot code review** — ревьюер как отдельная роль в PR.

### Msty (проверено 2026-10-09, msty.app)

Экосистема из четырёх продуктов:

- **Studio** — приватный чат-воркспейс (модели, knowledge, промпты).
- **Go** — ограниченные (bounded) агенты с пошаговым ревью исполнения.
- **Nexus** — локальный шлюз: провайдеры, ключи, политики, токены.
- **Stack** — версионируемые Knowledge Stacks ( governed RAG) — на момент проверки «coming soon».

### DeepSeek Harness / dsh (проверено 2026-10-10, github.com/deepseek-ai/deepseek-harness)

Открытый агентный харнесс от DeepSeek AI, архитектура «everything is a plugin» (на базе Cordis):

- **Запуск**: `npx @deepseek-ai/dsh web` → Web UI на localhost:3080; есть CLI-режимы и Python SDK. MIT.
- **Воркспейс** = каталог файловой системы: агент читает/правит файлы, запускает команды, ведёт план. Версионность — через git (как в opencode).
- **Субагенты нативно**: spawn/fork, настройки subagent, экспериментальный agent-team UI; есть интеграции subagent-claude-code / subagent-codex (внешние CLI-агенты как подчинённые).
- **HITL**: Web UI запрашивает подтверждение операций по активной permission policy.
- **Модели**: Settings → Models — DeepSeek API из коробки; гайд providers описывает других провайдеров и кастомные OpenAI-совместимые эндпоинты.
- **Роли/кастомизация**: агенты, инструменты, события — плагины (TypeScript/npm); готовых ролей-рецензентов нет, пишутся свои.
- **Статус**: developer preview, заявлены ломающие изменения — для регулярного процесса пока риск.

## Паттерны взаимопроверки (если писать самому)

1. **Generator–Critic**: агент A пишет, агент B (другой промпт/модель) ревьюит по чек-листу, A правит. 2–3 итерации.
2. **LLM-as-judge**: два агента независимо пишут/проверяют, третий выносит вердикт.
3. **Debate**: редактор vs ревьюер спорят N раундов, арбитр фиксирует итог.

Ключевые приёмы: разные модели для генератора и критика; свежий контекст ревьюера (иначе «дрейфует» в снисходительность); формальный чек-лист вместо «проверь всё».

## Вердикт (промежуточный)

- **Msty** закрывает human-in-the-loop, роли, провайдеров и RAG «из коробки», но:
  - цикл «редактор → ревьюер → правка» с заданным числом итераций — вручную (копировать вывод рецензента обратно редактору);
  - версионность документа — слабое место (Stack ещё не вышел).
- Если итерации и версионность критичны — **CrewAI + git** (скрипт ~100 строк, агент настроит за вечер) либо **opencode с субагентами** (git даёт версии, роли/итерации задаются промптом, апрув на каждом шаге).
- Прагматичный гибрид: документ живёт в git-каталоге, Msty — «пульт» ревью с разными провайдерами и RAG.
- **DeepSeek Harness** — сильный кандидат «на вырост»: нативные субагенты, HITL, плагинная кастомизация ролей, DeepSeek-модели (дешёвый критик) + OpenAI-совместимые эндпоинты; сдерживает developer preview и отсутствие готового RAG. Для regular-процесса сейчас надёжнее opencode/CrewAI, dsh — наблюдать и пилотить параллельно.

## Пример использования opencode (демо сессии)

Схема: git-репозиторий = версионность и «одно место»; роли = субагенты/кастомные агенты (`.opencode/agent/*.md` или `skills/`); итерации = число в промпте; HITL = permission `ask` + просмотр diff перед коммитом; RAG = Obsidian (LAPIM) / pdf-brain; провайдеры = `/models`, у ревьюера может быть другая модель.

Демо: субагент `reviewer` отревьюил этот файл по чек-листу → **NEEDS_CHANGES**, 8 замечаний (3 критично: противоречие «Msty RAG ✔» vs «Stack coming soon»; требование 1 «без перетаскивания файлов» потеряно в таблице и вердикте; кандидаты Cursor/Copilot/OpenAI SDK не вошли в таблицу без причины отсева; 4 — желательно). Полный текст вердикта не применялся (пользователь продолжил).

## Оценка скиллов для рецензирования стандарта проектирования моделей данных

Контекст каталога: каркас стандарта `Структура стандарта КМД и ЛМД v0.2…v0.7` (версионирование копиями файлов), 5 файлов «Рецензия …» от 2026-10-09 (ручные итерации ревью), глоссарий, примеры (md, docx, xlsx), метамодель.

### Что уже есть

| Ресурс | Покрытие |
|---|---|
| `skills/data-modeling/SKILL.md` (проектный) | ✔ чек-лист ревью **модели** (концептуальный/логический уровень), анти-паттерны, словарь данных. Но это ревью модели, **не стандарта** |
| Субагент `reviewer` (встроенный) | ✔ общий ревью по чек-листу, без доменной специфики |
| `officecli` | ✔ чтение/проверка .docx и .xlsx (артефакты стандарта: `Стандарты_LDM_примерБанка.docx`, `Метамодель_модели_данных.xlsx`) |
| `obsidian` (vault LAPIM) | ✔ RAG-база терминов и методматериалов при ревью |
| Файлы «Рецензия …» (5 шт.) | ✔ сырьё: из них дистиллируется доменный чек-лист ревью стандарта |

### Чего не хватает (гэпы)

1. **Скилл «ревью стандарта»** — сам файл `data-modeling/SKILL.md` (строка «Границы навыка») заявляет: «Проверка соответствия корпоративному стандарту — отдельный навык ревью (в плане создания)». Не создан. Должен покрывать: полноту структуры стандарта (цели, область, терминология, нотация, правила именования, уровни КМД/ЛМД, управление изменениями, роли, шаблоны артефактов), согласованность метамодель ↔ стандарт ↔ глоссарий, готовность к пилоту (AS-IS), внутреннюю непротиворечивость каркаса.
2. **Протокол вердикта** — фиксация формата (APPROVED / NEEDS_CHANGES + серьёзность + ссылка на раздел) как общий стандарт ревью для всех ролей.
3. **Роли-промпты** — методолог / архитектор НСИ / практик-пилот с разными фокусами (сейчас роли живут разово в промптах чата).
4. **Связка «число итераций»** — параметр цикла редактор↔ревьюер в воспроизводимой форме (сейчас задаётся руками каждый раз).

### Вывод

База есть (чек-лист моделей, инструменты чтения артефактов, RAG, сырьё из 5 рецензий); ключевой гэп — один доменный скилл ревью стандарта + кодификация ролей и протокола вердикта. Создаётся за одну сессию: дистилляция чек-листа из существующих рецензий + структура из `data-modeling`.

## Инструкция: рецензирование в opencode (промпт или скилл)

Три варианта — от быстрого к постоянному. Все используют одну схему: **редактор** = главный агент (правит, коммитит), **ревьюер** = субагент с другим контекстом/моделью (только читает, выносит вердикт), **человек** подтверждает каждое применение правок.

### 0. Подготовка каталога (однократно)

```bash
git init && git add -A && git commit -m "checkpoint: базовая версия"
```

Версионность = коммиты (`git diff`, `git log`), а не копии `v0.2…v0.7`. Перед каждой итерацией ревью — checkpoint-коммит, после применения правок — коммит `review iter N`.

### Вариант А. Промпт в чате (быстрый старт, ничего не создаём)

Промпт ревьюера (передать субагенту или вставить во вкладку с другой моделью):

```text
Ты — строгий независимый рецензент стандарта проектирования моделей данных.
Объект: <файл>. Только чтение, без правок.
Чек-лист: полнота структуры стандарта (цели, область, терминология, нотация,
именование, уровни КМД/ЛМД, управление изменениями, шаблоны артефактов);
согласованность метамодель ↔ стандарт ↔ глоссарий; готовность к пилоту;
внутренняя непротиворечивость.
Формат: ВЕРДИКТ: APPROVED|NEEDS_CHANGES; ЗАМЕЧАНИЯ: нумерованный список,
каждое [критично|желательно] + раздел + суть; ЧТО ХОРОШО: 2-3 пункта.
```

Промпт цикла для редактора (главный агент):

```text
Проведи N итераций рецензирования файла <файл>:
1) вызови субагента-ревьюера с чек-листом (промпт выше);
2) покажи мне замечания и жди подтверждения — какие применять;
3) примени только подтверждённые, покажи diff, закоммить "review iter K";
4) повтори. Без моего подтверждения не правь и не коммить.
```

### Вариант Б. Кастомные агенты — постоянные роли

`.opencode/agent/reviewer-standard.md`:

```markdown
---
description: Рецензент стандарта КМД/ЛМД. Вызывать для ревью документов стандарта и его структуры.
mode: subagent
model: <провайдер/модель, отличная от редактора>   # разные модели для генератора и критика
---
Ты — строгий независимый рецензент стандарта проектирования моделей данных.
Только чтение. Чек-лист: <как в промпте варианта А; при наличии скилла —
«применяй скилл data-model-standard-review»>.
Формат: ВЕРДИКТ: APPROVED|NEEDS_CHANGES; ЗАМЕЧАНИЯ: [критично|желательно] + раздел + суть; ЧТО ХОРОШО.
```

`.opencode/agent/editor.md` (`mode: primary`) — редактор: применяет только подтверждённые человеком правки, коммитит по итерациям, ведёт журнал в md-файле сессии.

### Вариант В. Скилл — доменная экспертиза ревьюера

`.opencode/skills/data-model-standard-review/SKILL.md` (или `skills_create`):

```markdown
---
name: data-model-standard-review
description: >
  Ревью стандарта проектирования моделей данных (КМД/ЛМД): структура,
  полнота, согласованность с метамоделью и глоссарием, готовность к пилоту.
  Использовать при рецензировании документов стандарта. НЕ для ревью самих моделей (см. data-modeling).
---
# Чек-лист ревью стандарта
1. Полнота структуры: цели/область/терминология/нотация/именование/уровни/процессы/шаблоны
2. Согласованность: метамодель ↔ стандарт ↔ глоссарий (термин — одно определение)
3. Готовность к пилоту: достаточно ли указаний для наполнения AS-IS
4. Непротиворечивость: версии каркаса, таблицы vs текст
5. Артефакты: docx/xlsx читаются через officecli
## Протокол вердикта
ВЕРДИКТ: APPROVED|NEEDS_CHANGES + ЗАМЕЧАНИЯ [критично|желательно] + ЧТО ХОРОШО
```

Чек-лист наполняется дистилляцией 5 существующих файлов «Рецензия …» + разделов `skills/data-modeling`.

### Human-in-the-loop

`opencode.json` (в корне каталога):

```json
{ "permission": { "edit": "ask", "bash": "ask", "webfetch": "ask" } }
```

Правило процесса: правка → показ diff → подтверждение человека → коммит. Ревьюер правок не делает вообще.

### Смена провайдеров

- `/models` — сменить модель текущей сессии на лету;
- поле `model:` в frontmatter агента — у ревьюера фиксированная другая модель/провайдер;
- провайдеры: `opencode auth login` или блок `provider` в `opencode.json`.

### RAG при ревью

- файлы каталога (глоссарий, метамодель, рецензии) — агент читает напрямую;
- .docx/.xlsx — через officecli; база знаний Obsidian (LAPIM) — скилл `obsidian`;
- RAG через MCP — да, opencode является MCP-клиентом:
  - подключение: `opencode mcp add <имя> -- <команда>` или блок `mcp` в `opencode.json`;
  - в этой сессии уже подключены: `pdf-brain` (семантический поиск по PDF/MD, эмбеддинги локально через Ollama), `lean-ctx` (семантический поиск по файлам);
  - сторонние варианты: IBM `mcp-rag-local` (ChromaDB + локальные эмбеддинги), MCP-серверы для Obsidian (база LAPIM);
  - пример конфига:
    ```json
    { "mcp": { "rag": { "type": "local", "command": ["npx", "-y", "mcp-rag-local"], "enabled": true } } }
    ```
  - в чек-лист ревьюера добавляется шаг «терминология: проверить по базе знаний через RAG-поиск»; в промпте ревьюера явно указывается, каким MCP-инструментом пользоваться.

### Типовой цикл (пример)

1. `opencode` в каталоге стандарта.
2. «Открой "Структура стандарта КМД и ЛМД v0.7…", запусти ревьюера-стандарта, 2 итерации».
3. Читаю замечания → «Применить 1, 3, 4; п. 2 отклоняю, потому что …».
4. Редактор правит, показывает diff → «Коммить: review iter 1».
5. Итерация 2 → APPROVED или список остаточных замечаний в журнал.
6. История версий: `git log --oneline`; откат: `git revert`.

## Уточнение области: разовое vs регулярное

- **Подготовка стандарта — разовая активность.** Ревью каркаса/стандарта — временный процесс (вариант А: промпты в чате + git-версии) на период доработки до финальной версии. Отдельный постоянный скилл «ревью стандарта» не нужен.
- **Проверка моделей на соответствие стандарту — регулярная.** Это и есть главный постоянный актив:
  - скилл/агент `compliance-review` (проверка модели против финального стандарта) — именно он заявлен в `skills/data-modeling/SKILL.md` как «в плане создания»;
  - RAG-база = зафиксированный финальный стандарт + глоссарий (неизменный корпус для регулярных проверок);
  - вход: модель (md/ER-диаграмма, docx через officecli, xlsx) → ревьюер-субагент (чек-лист `data-modeling` + RAG по стандарту) → вердикт APPROVED/NEEDS_CHANGES → человек подтверждает правки → коммит.
- Следовательно, порядок работ: (1) доработать стандарт разово — промпт-ревью + git; (2) зафиксировать релиз стандарта (коммит/тег); (3) собрать постоянный конвейер compliance-проверки моделей (скилл + агент + RAG по релизу стандарта).
