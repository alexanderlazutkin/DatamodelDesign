# Корпоративный стандарт проектирования, документирования и сопровождения концептуальных и логических моделей данных

**Версия: 0.8 — базовая структура двухдокументного комплекта (стандарт + регламент AS-IS, см. 1.8); подготовлена для AS-IS-пилота (учтены рецензии v0.2–v0.6)**

Стандарт объединяет общие правила управления моделями и отдельные требования к КМД и ЛМД. Структура охватывает **TO-BE, AS-IS и смешанный режим** и учитывает рекомендации по результатам анализа банковского примера. Нормативный комплект состоит из настоящего стандарта (целевые и общие нормы) и отдельного регламента восстановления и документирования AS-IS, связанного со стандартом полной матрицей применения требований, — см. 1.8.

Требования расположены преимущественно в порядке применения:

**определение задачи → подготовка оснований → КМД → ЛМД → проверка соответствий → приёмка → сопровождение.**

Подробные правила физического проектирования и инструкции по работе в конкретном инструменте оформляются отдельными документами. Оглавление и состав основных приложений зафиксированы; изменения допускаются по результатам пилотного применения (12.2), а также при выявлении существенного противоречия, изменении обязательных внешних требований или по решению утверждающего органа. Прочие предложения накапливаются в реестре замечаний пилота.

## Как пользоваться структурой

Настоящий документ — базовая структура стандарта, зафиксированная для пилотного наполнения (12.2). Правила чтения:

1. **Пункты списков внутри разделов задают обязательный охват будущей проработки.** Формулировки пунктов — рабочие тезисы, а не окончательные нормативные требования; требования фиксируются с присвоением ID.
2. Маркер **[Заполняется]** отмечает места, требующие данных конкретной организации (перечни документов, сроки, наименования систем).
3. Перекрёстные ссылки приведены в формате «см. N.M»; авторитетное место требования указано явной ссылкой и продублировано в карте перекрёстных ссылок (приложение У).
4. Идентификаторы требований (`GEN-xxx`, `CDM-xxx`, `LDM-xxx`, см. 3.9) присваиваются при наполнении. Ориентировочное распределение: разделы 3–5, 8, 10–12 — преимущественно `GEN`; раздел 6 — `CDM`; раздел 7 — `LDM`.
5. Требования ведутся в **машиночитаемом реестре** (приложение А) по правилам двойного представления (3.11); прослеживаемость к исходным требованиям обеспечивается приложением **Ф**.

## 1.8. Состав нормативного комплекта и регламент AS-IS

- Нормативный комплект образуют **настоящий стандарт** — целевые нормы проектирования (TO-BE) и общие нормы (термины, идентификация и жизненный цикл требований, применимость, метаданные, прослеживаемость, проверка, репозиторий и сопровождение), — и отдельный **регламент восстановления и документирования AS-IS** (далее — регламент AS-IS).
- Регламент AS-IS развивает специальный порядок раздела 9, допущения 3.7 и приемку этапов AS-IS (10.5). До выпуска регламента его будущие нормы действуют в составе настоящего стандарта; при выпуске комплекта они переносятся в регламент по правилам жизненного цикла идентификаторов (3.9) без изменения обязательств.
- Регламент AS-IS содержит **полную матрицу применения и адаптации требований** настоящего стандарта: для каждого требования заявленного выпуска — способ применения (без изменения / адаптировано / не применяется), ссылка на адаптированное либо специальное требование AS-IS, обоснование различия и критерий проверки в AS-IS (схема — приложение А). Матрица устанавливает применение норм, а не результаты проверки: записи соответствия конкретных моделей ведутся отдельно по приложению А и в матрицу не входят.
- Мастер-источник обоих документов — единый реестр требований (3.11): одинаковое обязательство имеет один идентификатор и применяется в обоих документах (связь «применяется без изменения»); при различии обязательств вводятся отдельные требования со связью «адаптирует для режима»; специальные требования AS-IS без целевого аналога получают собственные идентификаторы с применимостью по режиму. Связи `replaces` для режимных связей не применяются: регламент AS-IS не выводит требования стандарта из действия.
- Выпуск регламента AS-IS фиксирует выпуск настоящего стандарта, с которым он согласован, через механизм манифеста (11.7, приложение А); применение рассогласованных выпусков не допускается.
- Смешанный режим (3.3) сохраняется: к фрагментам по их состоянию применяются нормы соответствующего документа комплекта через ось `mode` реестра; разграничение состояний — по 3.4.

# 2. Термины, архитектура моделей и основные принципы

## 2.1. Термины и сокращения

Обязательный минимум терминов, определения которых фиксируются в стандарте:

- КМД, ЛМД, ФМД; домен, модель, представление, диаграмма;
- **ИОД — информация ограниченного доступа**: единый термин для разметки чувствительных данных во всех разделах стандарта (см. 6.14, 7.15, приложение И);
- TO-BE, AS-IS; регламент AS-IS; матрица применения требований (1.8); соответствие; паспорт модели; профиль моделирования;
- бизнес-идентичность, ассоциативная сущность, домен атрибута;
- вид утверждения, отнесение к состоянию, характер изменения, статус подтверждения, механизм контроля (5.7, 5.8, 8.9, 9.6);
- [Заполняется: полный глоссарий по результатам наполнения]

Термины получают идентификаторы `T-xxx` для ссылок и машиночитаемого глоссария (3.11).

Примечание: разговорный термин «чувствительные данные» в тексте стандарта не используется; применяется единый термин **ИОД**.

## 2.2. Уровни моделирования

### 2.2.1. Карта предметных областей

Обзор доменов, их назначения, владельцев и основных зависимостей.

### 2.2.2. Концептуальная модель данных

Бизнес-понятия, идентичность, связи и существенные правила независимо от реализации.

### 2.2.3. Логическая модель данных

Детализированные сущности, атрибуты, домены, идентификаторы, связи и ограничения.

### 2.2.4. Физическая модель данных

Реализация логических структур в выбранной технологии; граница ответственности настоящего стандарта.

## 2.3. Виды моделей по назначению и охвату

- Корпоративная.
- Доменная.
- Системная.
- Проектная.

**Уровень абстракции и охват являются независимыми характеристиками:** например, проект может включать и КМД, и ЛМД.

## 2.4. Профили моделирования

- Корпоративная интеграционная модель.
- Системная реляционная модель.
- Аналитическая модель.
- Документная и полуструктурированная модель.
- Иные утверждённые профили.

Для каждого профиля устанавливаются применимые конструкции и особенности структурной проверки (см. приложение Б).

Основная область применения профилей — ЛМД. Для КМД профили применяются в исключительных случаях по решению архитектора данных; решение фиксируется в паспорте модели (5.1).

Модель может относиться к нескольким профилям одновременно: применяются требования всех профилей. Профиль может назначаться **отдельному пакету или фрагменту** составной модели, а не только модели целиком. Конфликт требований профилей разрешается архитектором данных с фиксацией решения в реестре решений (8.1); решение определяет применимый профиль, область его действия или способ совместного выполнения требований. Если решение предполагает невыполнение применимого обязательного требования, оформляется исключение по 3.8.

## 2.5. Домен, пакет модели и представление

Различение:

- бизнес-домена;
- группы объектов репозитория;
- модели;
- представления;
- диаграммы.

## 2.6. Соотношение КМД, ЛМД и ФМД

- Допустимая детализация.
- Соответствия 1:1, 1:N и M:N.
- Технические элементы без самостоятельного концептуального аналога.
- Сохранение бизнес-семантики при преобразовании.

Нормативные требования к фиксации соответствий — в разделе 8 (8.4–8.6); настоящий раздел определяет понятийную основу.

- Бизнес-глоссарий.
- Словарь именования.
- Каталог логических доменов.
- Каталог бизнес-правил.
- Модель данных.
- Модель сообщения.
- Описание происхождения данных.

## 2.8. Основные принципы моделирования

- Бизнес-смысл первичен по отношению к структуре хранения.
- Диаграмма является представлением модели.
- Полнота определяется согласованным охватом.
- Структурное сходство не доказывает смысловую тождественность.
- Отсутствие сведений не означает отсутствия понятия или правила.
- Наблюдения в данных не становятся правилами автоматически.
- Недостатки реализации не должны скрываться при документировании.

# 3. Режимы применения и система требований

## 3.1. TO-BE — проектирование

- Цель режима: создание целевых моделей для новых и изменяемых систем, контрактов, аналитических решений.
- Исходная позиция: требования, целевые бизнес-процессы, референтные модели, информационные потребности (5.5–5.6).
- Применяются требования разделов 6–8 в полном объёме, с учётом применимости (3.5).
- Целевые утверждения характеризуются отнесением к состоянию TO-BE и характером изменения (5.7) с указанием основания (инициатива, требование).
- Результат режима: состав создаваемых и изменяемых моделей определяется заданием и охватом. Использование существующей КМД вместо разработки новой фиксируется ссылкой на её утверждённую версию. Результат включает соответствия и комплект публикации (11.6) для созданных или изменённых моделей.

## 3.2. AS-IS — восстановление и документирование

- Цель режима: достоверная фиксация существующего положения данных и семантики.
- Источники: реализация систем, структуры данных, код, существующая документация, эксперты, профилирование данных.
- Применяются требования разделов 6–8 с допущениями восстановления (3.7); специальный порядок — раздел 9 (нормативная основа регламента AS-IS — 1.8).
- Статусы подтверждения: «подтверждено», «предположение», «не установлено», «противоречие источников» (5.8); маркировка обязательна.
- Запрет подмены: наблюдаемое состояние фиксируется как есть; целевые предложения оформляются отдельно (9.10).

## 3.3. Смешанный режим

- Определение: в одной работе сочетаются восстановление фрагмента AS-IS и проектирование целевого изменения.
- Типовые случаи: обследование с последующим перепроектированием; миграция и консолидация; эволюция унаследованных систем.
- Обязательное условие: разграничение состояний по 3.4; приёмка — по двойному контуру (10.6).
- Порядок распространения требований: к AS-IS-фрагменту применяются допущения 3.7 и раздел 9; к целевому фрагменту — полный объём разделов 6–8 с учётом применимости по 3.5. Применимость требований в смешанном режиме определяется отдельно для фрагментов по их состоянию (приложение А).

## 3.4. Разделение текущего состояния и целевых изменений

- Требования к раздельному представлению: целевые элементы не смешиваются с зафиксированными в одном представлении без явной маркировки.
- Способы разделения: ветви/версии модели, слои, отдельные представления — выбираются при планировании (5.10).
- Маркировка целевых элементов: отнесение к состоянию TO-BE и характер изменения (5.7), ссылка на инициативу/требование.
- Трассировка перехода: соответствия «AS-IS → целевое» для миграционных изменений (дополняет 8.4–8.6).

## 3.5. Применимость требований

Применимость определяется по:

- уровню модели;
- профилю;
- режиму;
- согласованному охвату;
- этапу работ;
- наличию соответствующей конструкции.

Значения критериев применимости указываются в реестре требований (3.11, приложение А) в машиночитаемой форме; семантика отсутствия, неопределённости, этапа, смешанного режима и условий — в приложении А.

## 3.6. Нормативная модальность требований и результаты проверки

Модальность выражает характер требования, а не степень его важности:

- **Предписание** («должен», «обязательно»): невыполнение — основание для непринятия (10.10); отклонение — только через процедуру исключения (3.8).
- **Запрет** («не допускается»): форма обязательного требования; нарушение — основание для непринятия (10.10).
- **Рекомендация** («рекомендуется»): выполняется по умолчанию; отклонение фиксируется в реестре решений, если влияет на структуру модели, семантику или соответствия; процедура исключения не требуется. Незначительный выбор варианта фиксации не требует записи.
- **Разрешение** («допускается»): вариативность приемлемых вариантов; выбор варианта не требует обоснования, если иное не следует из требования.

Предписания и запреты образуют множество **обязательных требований**. «Не применимо» используется как результат проверки с обоснованием. Соответствие кодов модальности реестра — приложение А.

## 3.7. Допущения при восстановлении AS-IS

- Рабочие определения и временные наименования.
- Неустановленные ограничения.
- Предварительные соответствия.
- Частичная семантическая проработка.
- Обязательная маркировка и учёт открытых вопросов.

Каждое допущение фиксируется со статусом подтверждения (5.8) и планом уточнения (9.9).

## 3.8. Исключения из стандарта

- Состав записи об исключении: основание, влияние, ответственный, согласовывающий, условия и срок пересмотра.
- Перечень требований, допускающих и не допускающих исключений, согласовывается с ИБ и юридической функцией. [Заполняется: перечень]
- Различаются: внешнее обязательство, которое исключением не отменяется, и способ документирования, особенности которого могут допускать исключение.
- Полномочия на согласование исключений — по матрице ответственности (приложение К).
- Внутреннее исключение не отменяет применимых внешних обязательств (законодательство, регуляторные требования).

## 3.9. Идентификация и жизненный цикл требований

- `GEN-xxx` — общие требования.
- `CDM-xxx` — требования к КМД.
- `LDM-xxx` — требования к ЛМД.

Правила жизненного цикла идентификатора:

- перенос требования без изменения обязательства — ID сохраняется;
- редакционная правка — ID сохраняется, редакция записи меняется;
- разделение или объединение обязательств — присваиваются новые ID со связями преемственности (`replaces`, `refines`);
- выведенные из действия ID повторно не используются.

При несовпадении префиксов идентификаторов исходных документов соответствие фиксируется таблицей переноса (приложение Ф).

## 3.10. Правила формулирования и ведения требований

- **Однократность**: каждое нормативное требование формулируется один раз и имеет стабильный ID; пояснения размещаются рядом с требованием; реестр требований (приложение А) содержит его структурированное представление.
- **Атомарность**: одно требование устанавливает одно самостоятельно проверяемое обязательство; независимые обязательства разделяются; логические условия и альтернативные способы выполнения допускаются при однозначном описании.
- **Предмет требования**: различаются требования к **проектному решению** (что должно быть определено и обеспечено в целевой модели), к **документированию** (полнота и корректность фиксации сведений в модели) и к **обследованию** (порядок установления и подтверждения сведений при восстановлении AS-IS). Требования формулируются не к предметным фактам: неизвестность факта при корректной фиксации не является невыполнением требования к документированию или обследованию. Например, требование «кардинальность связи задана установленным значением либо статусом неизвестности с основаниями и вопросом» выполнимо и при неизвестной кардинальности, а требование «кардинальность подтверждена» — нет. Допустимость неизвестности определяется применимостью требования, этапом и согласованным охватом, а не режимом работы самим по себе.
- **Тестируемость**: каждое требование имеет проверяемый критерий; обороты «по возможности», «в разумные сроки», «как правило» в нормативных формулировках не применяются.
- **Отсутствие дублирования**: связь с критериями проверки и историей изменений ведётся в реестре.
- TO-BE и AS-IS оформляются как особенности применения одного требования, если обязательство одинаково; при различии обязательств вводятся отдельные требования со связью «адаптирует для режима» (1.8). Полнота связи документов комплекта поддерживается матрицей применения требований регламента AS-IS.
- Методические примеры не вводят новых обязательств.
- Изменения структуры стандарта (перенос, слияние, разделение разделов) выполняются по правилам жизненного цикла ID (3.9) и отражаются в таблице переноса (приложение Ф).

## 3.11. Машиночитаемое представление и границы автоматизации

**Двойное представление и мастер-источник:**

- Человекочитаемый текст стандарта и машиночитаемый реестр требований (приложение А) описывают одни и те же требования.
- Мастер-источник — реестр: текст стандарта формируется из реестра либо проходит автоматическую проверку консистентности с ним. Две независимо редактируемые копии нормативной формулировки не допускаются.
- Глоссарий ведётся как машиночитаемый словарь терминов `T-xxx` (2.1); контрольные процедуры (приложение Ж) и матрица ответственности (приложение К) — в структурированном виде со ссылками на ID.

**Авторитетное представление моделей:**

- Хранилище модели должно обеспечивать структурированное хранение элементов, идентификаторов, связей и обязательных метаданных; допускаются репозитории инструментов моделирования и текстовые форматы, соответствующие требованиям полноты и переносимости; диаграммы формируются как представления модели (2.8).
- Текстовые форматы обязательны для артефактов самого стандарта (реестр требований, глоссарий, контрольные процедуры).
- Сканы и скриншоты не применяются как машиночитаемое представление нормативного содержания; как источники обследования при AS-IS допускаются с фиксацией ограничений (9.5).

**Границы автоматизации и применения ИИ:**

- Различаются детерминированная проверка (автоматизируемая: например, наличие домена у атрибута) и экспертная оценка (требующая уполномоченного эксперта: например, корректность бизнес-идентичности).
- **Итоговое решение остаётся за уполномоченным проверяющим (10.11). Результаты утверждённых автоматизированных детерминированных процедур могут приниматься в качестве достаточного свидетельства без ручного повторения при соблюдении условий их применимости.** Выводы ИИ, требующие смысловой интерпретации, рассматриваются отдельно и сами по себе свидетельством не являются.
- Применение автоматизации подчиняется правилам доступа (11.10), включая запрет передачи материалов модели в несогласованные сервисы.
- Воспроизводимость: при использовании автоматизированного результата в приёмке сохраняются исходная версия материалов, средство проверки и существенные параметры.

**Навигация для автоматизированных средств:**

- Ведётся индекс «задача → разделы» (маршруты поиска).
- Самодостаточность при фрагментарном чтении обеспечивается явными ссылками на определения, применимость и зависимости — а не повторением содержания (запрет дублирования, 3.10).

Распределение «роль × этап × артефакт» — в матрице ответственности (приложение К); в ней отдельно закрепляются полномочия: утверждение бизнес-семантики, принятие архитектурных решений, согласование исключений (3.8), разрешение публикации, принятие риска остаточного вопроса (10.9).

## 4.2. Этапы проектирования и результаты этапов

1. Постановка задачи.
2. Определение охвата и оснований.
3. Разработка КМД.
4. Согласование концептуальной семантики.
5. Разработка ЛМД.
6. Проверка моделей и соответствий.
7. Приёмка и публикация.

Для каждого этапа фиксируются: входные условия, результаты, ответственные роли, критерии перехода (4.3). Нумерация и наименования этапов используются как классификатор в реестре требований (приложение А).

## 4.3. Условия перехода между этапами

Параллельная разработка, промежуточное согласование и условия окончательного утверждения.

Порядок работ определяется планом обследования (9.1); нумерация этапов (4.2) не устанавливает обязательную хронологию их выполнения.

## 4.4. Корпоративное и проектное моделирование

- Использование общих понятий.
- Локальные проектные расширения.
- Включение проектных решений в корпоративные модели.
- Разрешение междоменных разногласий.

- Условия использования материалов.
- Проверка применимости.

Методика адаптации и примеры соответствий — приложение М.

- Авторитетная утверждённая версия.
- Рабочие версии или ветви.
- Связь с исходной базовой версией.
- Состав пакета изменений.

## 4.7. Параллельная разработка и объединение изменений

- Выявление конфликтов.
- Проверка актуальности базовой версии.
- Согласование изменений общих элементов.
- Полномочия на включение изменений.

## 4.8. Управление вопросами, решениями и отклонениями

Единая точка учёта вопросов по моделям, включая расхождения и несопоставленные элементы (8.10). Раздельный учёт категорий записей:

- пробелы документации;
- ограничения обследования;
- конфликтующие трактовки;
- недостатки реализации;
- предложения развития;
- расхождения и несопоставленные элементы соответствий.

Каждая запись содержит: категорию, статус, ответственного, срок, влияние на модель. Первичный реестр формируется на этапе подготовки (5.9); пополнение при восстановлении AS-IS — через 9.8. Приёмка оперирует остаточными вопросами (10.9).

# 5. Подготовка моделирования: паспорт, охват и основания

## 5.1. Паспорт модели

Идентификатор, назначение, уровень, профиль, режим, охват, версия, статус, ответственные и дата актуальности.

Состав обязательных полей паспорта — приложение Г (минимальные метаданные). Паспорт создаётся до начала работ и актуализируется при смене статуса (11.9).

## 5.2. Границы моделирования

- Организационный, процессный и системный контекст.
- Включённые области.
- Исключения.
- Внешние понятия и зависимости.
- Охват текущего этапа.

Изменение границ согласовывается в том же порядке, что и исходный охват; обнаруженные за границами зависимости регистрируются для оценки влияния (8.11), но не становятся автоматически обязательством текущего этапа.

## 5.3. Инвентаризация источников

Документы, требования, процессы, глоссарий, модели, интерфейсы, приложения, структуры данных и экспертные сведения.

Для каждого источника фиксируются: тип, версия/дата, доступность, актуальность. При AS-IS инвентаризация расширяется состоянием источников (9.2).

## 5.4. Применимые политики и контракты

Требования ИБ, хранения, удаления, аудита, интеграции и качества данных, влияющие на модель.

Отдельно фиксируются требования к разметке ИОД (приложение И) и ограничения распространения артефактов (11.10).

## 5.5. Приоритетные понятия и информационные потребности

- Перечень критичных для задачи понятий: кто и в каких решениях ими оперирует.
- Информационные потребности стейкхолдеров: какие сведения, с какой периодичностью и детализацией необходимы.
- Связь потребностей с показателями, отчётностью и сценариями (5.6).
- Использование перечня: ограничение охвата этапа, приоритизация проработки, критерий достаточности при приёмке.

## 5.6. Типовые и граничные бизнес-сценарии

- Состав: типовые, граничные, исключительные и негативные сценарии; для каждого — входные условия, участники, результатные сведения.
- Назначение: проверка полноты и корректности КМД (6.15) и сценарная проверка (10.1).
- Форма фиксации: каталог сценариев, связанный с приоритетными понятиями (5.5).
- Правило: сценарии согласуются с владельцем бизнес-семантики и включаются в комплект проверки.

## 5.7. Характеристики утверждений: вид, состояние, источники

Характеристики задаются раздельно и не сводятся к одной; указываются для **существенных утверждений об элементах** (не только для элементов целиком: определение сущности может быть подтверждено, а кардинальность одной из её связей — не установлена):

- **Вид утверждения**: определение понятия / бизнес-правило / описание реализации / наблюдение.
- **Отнесение к состоянию**: AS-IS / TO-BE; по умолчанию наследуется от версии модели и указывается явно только при отклонении (3.4).
- **Характер изменения**: добавлено / изменено / исключено / без изменения — определяется **относительно указанной базовой версии или пакета изменений (4.6)**; вне сравнения версий признак не задаётся.
- **Источники**: указываются множественно, с ролью источника — подтверждает / противоречит (основа фиксации противоречий, 5.8); при фиксации противоречий указываются контекст и период действия утверждений — правила разных периодов или контекстов не обязательно противоречат друг другу.
- **Статус подтверждения** — 5.8.

Механизм контроля ограничений — отдельная характеристика (8.9, 9.6). Метаданные карточки утверждения — приложение Г.

## 5.8. Статусы подтверждения и правила их изменения

- Статусы: подтверждено / предположение / не установлено / противоречие источников.
- Правила смены статусов (общие для TO-BE и AS-IS): основание, источник, дата; история изменений статуса сохраняется.
- Статус «противоречие источников» присваивается с учётом контекста и периода действия утверждений (5.7) и требует записи в реестре вопросов (4.8).
- Особенности поэтапного уточнения статусов при AS-IS — 9.9.

## 5.9. Первичный реестр вопросов и ограничений

- Формируется по результатам инвентаризации (5.3) и анализа оснований (5.4).
- Классификация записей — по категориям 4.8.
- Каждая запись: формулировка, категория, статус подтверждения (5.8), предварительный ответственный.
- Первичный реестр — вход этапа моделирования; далее ведётся в едином учёте 4.8, дополняясь при AS-IS (9.8).

## 5.10. План работ и условия приёмки этапа

- Состав работ, последовательность и результаты этапа; способ разграничения AS-IS/TO-BE при смешанном режиме (3.4).
- Условия приёмки этапа: ссылаются на согласованный охват (5.2) и виды проверки (10.1), а не на универсальный процент готовности.
- Глубина семантической проработки этапа устанавливается планом (включая AS-IS-этапы).
- Ресурсы, сроки, ответственные роли (приложение К).
- Условия пересмотра плана: изменение охвата, выявленные ограничения, новые вопросы категории «противоречие».

# 8. Прослеживаемость и сохранение семантики

*Авторитетный раздел для всех видов соответствий (см. также карту перекрёстных ссылок — приложение У).*

## 8.1. Связи с требованиями, источниками и решениями

- Трассировка «требование → элемент модели»: для существенных элементов фиксируется породившее требование или информационная потребность (5.5).
- **Для AS-IS основанием включения элемента в модель может быть зафиксированное наличие элемента в обследованной реализации в пределах согласованного охвата.** Исходное требование указывается при его наличии; отсутствие сведений о нём не восполняется предположением без маркировки. Различаются источник, подтверждающий существование структуры, и источник, подтверждающий её бизнес-смысл: наличие таблицы доказывает первое, но само по себе не доказывает второе (9.2).
- Указание источников сведений по 5.7: документ, система, эксперт — с ролью (подтверждает/противоречит), датой, актуальностью и результатами верификации; статус подтверждения относится к утверждению (5.8), а не к источнику.
- Реестр решений по моделированию: принятое решение, альтернативы, основание, автор, дата.
- Глубина трассировки: устанавливается по значимости элемента; минимальный охват — сущности, ключевые атрибуты, существенные связи и существенные правила.

## 8.2. Связи с бизнес-глоссарием

- Статусы определения: термин утверждён / предложен / отсутствует в глоссарии.

## 8.4. Соответствия КМД ↔ ЛМД

- Виды соответствий: 1:1, 1:N, M:N, «без концептуального аналога».
- Технические элементы: для элемента без концептуального аналога фиксируются назначение и основание включения — концептуальная конструкция, требование или архитектурное решение — в зависимости от происхождения элемента.
- Контроль сохранения семантики при переходе: потери, уточнения и изменения смысла фиксируются явно, а не молча.
- Полнота перехода: каждое понятие КМД в согласованном охвате имеет соответствие либо зарегистрированное обоснование отсутствия (8.10).

- Обязательные атрибуты записи: вид соответствия, причина, статус, ответственный, срок пересмотра.
- Правила допустимости пробелов: зависят от режима и этапа (для AS-IS — 9.11, для приёмки — 10.9).
- Эскалация длительно не закрытых записей изменяет уровень рассмотрения (ответственного и порядок), но не место учёта.

## 8.11. Анализ влияния изменений

- Сценарии анализа: изменение домена атрибута, ключей, кардинальностей, разбиение/слияние сущностей, изменение классификаторов.
- Источники данных для анализа: соответствия 8.3–8.7, разметка ИОД (6.14, 7.15), каталог правил.
- Результат: перечень затронутых моделей, представлений, контрактов и систем; требуемые изменения и порядок их внесения.
- Связь с пакетом изменений (4.6) и проверкой изменений (10.7).

# 9. Восстановление и документирование AS-IS

*Раздел определяет специальный порядок применения требований, не дублируя содержательные требования разделов 6–8. Раздел — нормативная основа отдельного регламента AS-IS (1.8); до выпуска регламента действует в составе настоящего стандарта.*

## 9.1. Планирование обследования и согласование охвата

- План обследования: перечень систем и структур, период данных, глубина рекурсии по зависимостям, состав экспертов; порядок выполнения работ, включая итеративную последовательность восстановления (4.3).
- Согласование охвата с владельцами систем и бизнес-семантики; фиксация в паспорте модели (5.1).
- Критерии достаточности этапа — из 9.11; охват может уточняться поэтапно.
- Ресурсы и доступы: согласование доступа к системам, структурам и данным с учётом ИОД (5.4).

## 9.2. Инвентаризация источников и фиксация их состояния

- Расширение инвентаризации 5.3: для каждого источника — состояние (актуален / устарел / недоступен / частично применим), дата, версия и способ извлечения сведений, способ верификации.
- Приоритет источников определяется **видом устанавливаемого утверждения**:
  - структура реализации подтверждается техническими источниками;
  - бизнес-смысл и нормативные ограничения — применимыми документами и уполномоченными владельцами семантики;
  - фактическое поведение — наблюдениями и проверками (9.7).
- Противоречия между источниками регистрируются (статус «противоречие источников», 5.8) и не устраняются автоматическим выбором одного источника.
- Результат: реестр источников обследования — вход для статусов подтверждения (5.8).

## 9.3. Восстановление КМД

- Отправные точки: инвентаризация (9.2), эксперты, существующие артефакты (документы, регламенты, отчёты); допускается восстановление после построения предварительной ЛМД (4.3).
- Выделение понятий из структур данных, процессов, документов и ролей; применение требований раздела 6 с допущениями 3.7.
- Маркировка предположений статусами подтверждения (5.8); рабочие определения допускаются с фиксацией в реестре вопросов (4.8).
- Итеративное уточнение — 9.9; проверка — 10.5.

## 9.4. Восстановление ЛМД

- Реконструкция из физических структур: таблицы, ключи, ограничения, представления, процедуры; допускается как отправной этап восстановления (4.3).
- Дополнение из кода приложений, сообщений и отчётов: фактические правила, не отражённые в структурах.
- Различение декларированного и фактически контролируемого — по 9.6; нереализованные ограничения фиксируются явно.
- Применение требований раздела 7 с допущениями 3.7; проверка — 10.5.

## 9.5. Обследование документов и полуструктурированных источников

- Виды источников: электронные документы, JSON/XML-структуры, отчёты, выгрузки, файловые обмены; допускаются сканы и изображения как источники обследования с фиксацией ограничений (3.11).
- Решение для каждого источника: извлекается ли семантика в модель или источник фиксируется как «чёрный ящик» с метаданными.
- Связь с моделированием документов как бизнес-объектов (6.12, 7.14) и полуструктурированных данных (7.13).
- Ограничения обследования (неполные выборки, недоступные архивы) фиксируются в реестре вопросов (4.8).

## 9.6. Характер связей, подтверждённость и механизмы контроля

Характеристики разделяются:

**Характер связи:**

- бизнес-отношение;
- техническая ссылка;
- кандидат на связь по наблюдаемым данным (9.7).

**Подтверждённость** — по статусам 5.8.

**Механизмы контроля** (по 8.9; возможно несколько одновременно):

- физически объявленное ограничение;
- контроль приложения;
- контроль загрузки;
- отдельная проверка.

Наличие механизма и статус его обследования фиксируются **отдельными полями** (значения «отсутствует» и «не установлен» описывают наличие и статус обследования, а не тип механизма): например, контроль СУБД установлен, а контроль приложения не обследован.

Наличие объявленного ограничения не доказывает, что оно включено и фактически проверяет все рассматриваемые данные.

**Результаты проверки** механизмов контроля фиксируются как свидетельства по приложению Г, связанные с объектом подтверждения (10.1); проверка выполнения требований стандарта оформляется отдельными записями (приложение А) — это разные объекты проверки.

Уточнение статусов — по правилам 5.8; особенности поэтапного уточнения при AS-IS — 9.9.

## 9.7. Профилирование данных и границы доказательности

Выборка, период, полнота обследования и запрет автоматического вывода бизнес-правил из наблюдений.

Результаты профилирования используются как вспомогательные свидетельства с указанием выборки и периода; свидетельство наблюдения не является доказательством правила.

## 9.8. Документирование неизвестного и противоречий

- Фиксация каждого установленного факта неизвестного: «не установлено» — тоже результат обследования.
- Противоречия источников: обе трактовки фиксируются со статусом «противоречие источников» (5.8).
- Категорирование неизвестного: пробел документации / ограничение обследования / конфликтная трактовка (по 4.8).
- Запрет: незаполненные сведения не маскируются правдоподобными дополнениями.

## 9.9. Поэтапное уточнение и экспертная проверка

- Цикл: фиксация → экспертная сессия → уточнение статусов (по правилам 5.8) → расширение охвата (9.1).
- Особенности AS-IS: состав экспертных сессий, порядок подтверждения предположений владельцами семантики.
- Критерий перехода к следующему этапу — из 9.11, а не субъективная «достаточность».

## 9.10. Отделение предложений TO-BE

- Предложения по изменению выявленного состояния регистрируются отдельно от результатов обследования.
- Форма: запись в категории «предложение развития» (4.8) со ссылкой на затронутые элементы.
- Запрет: целевые изменения не вносятся в зафиксированную AS-IS-модель до оформления разграничения (3.4).

## 9.11. Результаты и допустимые пробелы каждого этапа

- Результаты этапа: модель фрагмента, реестр источников (9.2), статусы подтверждения, реестр вопросов, перечень несопоставленных элементов (8.10).
- Допустимость пробела: **регистрация пробела — необходимое, но не достаточное условие его допустимости**. Пробел допускается, если не блокирует цели этапа либо принят уполномоченным лицом в установленном порядке (3.8).
- Недопустимый пробел: непокрытие обязательной части согласованного охвата без допустимого исключения.
- Обнаруженные за границами охвата зависимости регистрируются для оценки влияния (8.11) и не становятся обязательством текущего этапа.
- Приёмка результатов этапа — 10.5.

# 10. Проверка, согласование и приёмка

## 10.1. Виды проверки

Формальная, семантическая, структурная, межмодельная, экспертная и сценарная.

Набор применяемых проверок определяется применимыми требованиями (3.5); перечни в 10.2–10.6 задают минимальные акценты и не исключают иных проверок.

Различаются **объекты проверки**: выполнение требований стандарта (записи по приложению А) и соблюдение бизнес-ограничений (свидетельства по приложению Г); записи соответствия могут ссылаться на свидетельства. Свидетельство связывается с **объектом подтверждения**: утверждением, бизнес-правилом, элементом модели, процедурой или фактом выполнения организационного требования (8.9, 9.6).

Распределение с самопроверками: структурные проверки разработчика (6.15, 7.17) предшествуют организационной проверке настоящего раздела; их результаты включаются в комплект проверки.

## 10.2. Проверки по профилям моделирования

- Применимость конструкций профиля — по приложению Б; несоответствие профилю фиксируется как замечание.
- Профильные контрольные операции: реляционная модель — ссылочная целостность, нормализация/обоснование отклонений; аналитическая — гранулярность фактов, согласованность измерений; документная/полуструктурированная — схема контракта, версии расширений.
- Результаты профильных проверок выделяются в протоколе отдельным блоком.

## 10.3. Проверка КМД TO-BE

- Состав: формальная (полнота паспорта и метаданных), семантическая (определения, идентичность, границы), сценарная (по каталогу 5.6).
- Критерии — требования раздела 6; контрольный лист — приложение Ж.
- Участники: владелец бизнес-семантики, архитектор данных, технический эксперт — по матрице ответственности (приложение К).

## 10.4. Проверка ЛМД TO-BE

- Состав: структурная (7.17), межмодельная (соответствие КМД по 8.4), профильная (10.2), проверка разметки ИОД (7.15).
- Критерии — требования раздела 7; контрольный лист — приложение Ж.
- Проверка соответствий и прослеживаемости — по разделу 8.

## 10.5. Приёмка этапов AS-IS

- Критерии: соответствие модели обследованному состоянию; наличие проверяемых оснований существенных утверждений (5.7–5.8); полнота согласованного охвата; явный учёт неизвестного (9.8); различение характера связей, подтверждённости и механизмов контроля (9.6).
- Глубина семантической проработки определяется планом этапа (5.10), а не режимом как таковым: восстановленная КМД может требовать столь же подробных определений, как целевая.
- Не требуется: устранение недостатков реализации; приведение системы к целевой архитектуре. Допустимые пробелы — по 9.11.
- Экспертная валидация восстановленных фрагментов — по 9.9.

## 10.6. Приёмка смешанного режима

- Двойной контур: достоверность фиксации AS-IS-фрагмента (10.5) + качество целевого решения (10.3–10.4).
- Обязательная проверка разграничения состояний (3.4) и трассировки миграционных соответствий.
- Проверка, что предложения TO-BE зарегистрированы отдельно (9.10).

## 10.7. Проверка изменений

- Конфликты параллельной разработки.
- Совместимость доменов и контрактов.
- Влияние на связанные модели.
- Сохранение бизнес-правил.
- Основание — анализ влияния (8.11). **Объём повторной проверки определяется анализом влияния**: сокращённая проверка допускается при ограниченном и подтверждённом влиянии изменения. Изменения идентичности, гранулярности, кардинальностей, общей семантики, разметки ИОД и публичных контрактов требуют проверки всех затронутых зависимостей.

## 10.8. Показатели качества документации

Покрытие, семантическая проработка, связи, правила, прослеживаемость, открытые вопросы и актуальность.

Показатели рассчитываются относительно согласованного охвата (5.2) и применяются для сопоставимости этапов, а не как универсальный порог автоматической приёмки.

## 10.9. Допустимые остаточные вопросы и исключения

- Классификация остаточных вопросов по влиянию: блокирующее / ограничивающее / не влияющее на согласованный охват.
- Условия допустимости: маркировка в реестре (4.8), назначенный ответственный и срок закрытия, отражение в показателях (10.8); принятие риска остаточного вопроса — уполномоченным лицом по матрице ответственности (приложение К).
- Исключения из обязательных требований оформляются по 3.8 и перечисляются в протоколе.

## 10.10. Основания для непринятия

- Нарушение обязательных требований (предписаний и запретов по 3.6) без оформленного исключения (3.8).
- Отсутствие согласованного охвата; непокрытие его обязательной части без допустимого исключения; несогласованное изменение границ моделирования.
- Немаркированные неизвестные и подмена наблюдений предположениями (9.8).
- Неполные соответствия без регистрации (8.10); конфликты параллельной разработки (10.7).
- Порядок доработки: перечень замечаний, срок повторной подачи, повторная проверка затронутого объёма.

## 10.11. Протокол проверки и утверждение

- Состав протокола: объект и версия, применённые виды проверки (10.1), результаты по видам, замечания с классификацией (10.9), решение, подписи участников по ролям.
- Решение: принято / принято с замечаниями / не принято (основания — 10.10).
- **Связь результатов проверки с решением**: положительная приёмка обязательной части охвата требует подтверждённого выполнения применимых обязательных требований либо действующих оформленных исключений (3.8). При этом:
  - исключение не превращает результат `failed` в `verified`;
  - результат `not_applicable` требует обоснования;
  - результаты `not_checked` и `insufficient` не считаются выполнением;
  - решение «принято с замечаниями» не позволяет обойти блокирующее нарушение (10.10).
- Решения принимаются уполномоченными проверяющими; вспомогательные результаты автоматизированных средств и ИИ-агентов не заменяют этих решений (3.11).
- Протокол включается в комплект публикации (11.6) и хранится с историей модели (11.9).

## 10.12. Проверка согласованности публикуемого комплекта

- Проверка согласованности комплекта по манифесту выпуска (11.7): соответствие компонентов, их версий и источников манифесту.
- Контроль единообразия идентификатора выпуска во всех материалах комплекта.
- Контроль расхождений экспорта: сравнение опубликованных материалов с авторитетной моделью; зафиксированные расхождения устраняются до публикации.
- Выявленная потеря обязательных метаданных (11.8) не допускается к публикации до устранения.

# 11. Репозиторий, представления, публикация и сопровождение

## 11.1. Авторитетный источник модели

- Недопустимость несогласованных конкурирующих версий: **для каждого сочетания модели, состояния (AS-IS/TO-BE), области применения и периода действия однозначно определяется применимая утверждённая версия**; в одном контексте конкурирующие версии не допускаются.
- Применимая версия определяется по контексту и периоду действия. Если предусмотрен выбор по умолчанию, используется последняя утверждённая версия, **вступившая в действие для данного контекста и не отозванная**.
- Новый утверждённый TO-BE-выпуск не считается автоматически действующим AS-IS после внедрения: фактическое состояние подтверждается сверкой (11.12).
- Рабочие версии и ветви ведутся по 4.6–4.7 и авторитетными не являются.
- Определение авторитетного хранилища для каждой модели: репозиторий инструмента или управляемое файловое хранилище (3.11). [Заполняется: перечень]
- Сторонние копии не являются источником; порядок работы с копиями (срок действия, возврат изменений).
- Для файлового режима: процедуры блокировок, слияния и верификации целостности.

## 11.2. Идентичность элементов и пространства имён

- Стабильные внутренние идентификаторы элементов, не зависящие от наименований.
- Пространства имён: корпоративное, доменные, проектные; правила разрешения коллизий.
- Сохранение идентичности при импорте/экспорте и переносах (11.8).

## 11.3. Организация доменов, пакетов и представлений

Принадлежность элементов, повторное использование и различение удаления из представления и из модели.

## 11.4. Паспорт представления

Назначение, аудитория, охват, версия, уровень детализации и скрытые категории элементов. Состав полей — приложение Г.

- Публикация представлений выполняется по утверждённым профилям публикации (11.10).
- Скрытие пометки ИОД на представлении не изменяет метаданные модели и режим доступа к ней.

## 11.5. Нотация и читаемость диаграмм

Единая легенда, роли и кардинальности, обозначение внешних и неподтверждённых элементов; цвет не должен быть единственным носителем смысла.

Нормативная нотация — приложение В. Диаграммы формируются как представления модели (2.8); требования к авторитетному представлению модели — 3.11.

## 11.9. Жизненный цикл модели и версии

- Различаются жизненный цикл **модели** (как объекта сопровождения) и жизненный цикл её **версии** (выпуска).
- Статусы версии: черновик → на согласовании → утверждена → заменена / отозвана → архив. [Заполняется: при необходимости — дополнительные статусы организации] Статус «отозвана» присваивается версии при отзыве вследствие ошибки в самой утверждённой модели (11.13).

- Архивирование выполняется отдельно от замены (11.13).
- Состав записи истории: автор, дата, основание (пакет изменений 4.6, инициатива), краткое описание, связь с протоколом проверки (10.11).

## 12.2. Переходный период и пилотное применение

**Правила пилотирования:**

- Пилотное применение предшествует массовому переводу: стандарт отрабатывается на ограниченном наборе моделей; по результатам уточняются требования, схема реестра (приложение А), контрольные процедуры и профили публикации.
- Областью первого пилота является **AS-IS**. Практическая апробация механизмов, специфичных для TO-BE и смешанного режима, не входит в этап первого пилота; их методическая проверка и тестирование схемы реестра на синтетических примерах не исключаются. TO-BE-пример включается в пилот после появления исходных данных; смешанный режим — после включения TO-BE.
- Текущий состав моделей, доступные источники, сроки, ответственные и перечень проверочных случаев закрепляются в **плане AS-IS-пилота** (шаблон — приложение Л); состав пилотного фрагмента (одна КМД и связанная ЛМД восстановленного состояния, автоматическая и экспертная проверки, публикация по манифесту) также определяется планом. [Заполняется: ссылка на план AS-IS-пилота]
- Минимальная схема реестра утверждается до пилота (приложение А).
- Пилот проверяет матрицу применения требований AS-IS в объеме пилотного выпуска: полноту охвата требований среза, корректность способов применения и типовых связей (`applies_as_is` / `adapts_for_mode`).

**Проверочные случаи пилота: корректные, пограничные и ошибочные.**

- Типовые случаи: атрибут без домена (формальное замечание); неподтверждённая связь AS-IS с корректной маркировкой (оценка допустимости по целям этапа, а не автоматический отказ); обязательное требование с действующим исключением (невыполнение сохраняется в записи проверки, исключение учитывается при приёмке, 10.11); отозванная версия (не выбирается как действующая, 11.1); ошибка только в экспорте (не трактуется как ошибка исходной модели, 11.8, 11.13); изменение бизнес-ключа (запускает анализ влияния, 8.11). Полный перечень закрепляется в плане AS-IS-пилота.
- В состав случаев включается **пара, различающая невыполненное требование и корректно документированную неизвестность** (например, «кардинальность подтверждена» против «указано значение либо статус неизвестности с основаниями и вопросом»): неизвестность предметного факта не всегда означает неполноту его документирования (3.10). Цель — не оформлять массовые исключения там, где стандарт допускает корректно документированную неопределённость.
- Проверяются требования нормализации и именования: фиксация недостатка существующей реализации не требует её перепроектирования (10.5).
- **Изоляция проверочных случаев**: ошибочные ситуации вносятся только в изолированные тестовые копии моделей и публикаций; они не изменяют обследуемые системы, исходные свидетельства и авторитетный AS-IS-комплект. Для тестовой копии фиксируются базовая версия, внесённый дефект и ожидаемый результат проверки; тестовые копии получают идентификаторы в **пространстве имён тестовых артефактов**, отдельном от реестра моделей.
- Для случая «изменение бизнес-ключа» в плане указывается, что именно проверяется: уточнение ранее ошибочно восстановленного ключа, документирование реального изменения системы либо искусственное изменение тестовой копии; незаметный переход к проектированию TO-BE не допускается (9.10).

**Измерение и оценка трудоёмкости:**

- Измеряемые показатели: время моделирования; время заполнения метаданных; время проверки и согласования; количество повторно вводимых сведений; количество ручных действий при выпуске. Универсальный норматив времени до пилота не устанавливается.
- По результатам пилота отдельно оценивается **приемлемость** трудоёмкости и выявляются операции, требующие упрощения или автоматизации; результатом должно стать решение, а не только таблица затраченного времени.

**Оценка результатов пилота — три раздельных заключения:**

1. **О качестве восстановленной модели** — возможность принять AS-IS-документацию в согласованном охвате.
2. **О работоспособности стандарта** — однозначность требований, процедур и решений.
3. **О пригодности автоматизации** — корректность выбора применимых требований, выявления ошибок и формирования результатов.

Неприёмка тестовой модели с намеренной ошибкой может быть успехом проверки стандарта, а не неудачей пилота.

**Границы представительности и учёт покрытия:**

- Записи соответствия модели (приложение А) ведутся раздельно от **матрицы покрытия пилотом** требований, процедур, режимов и профилей (включается в отчёт пилота): `not_applicable` для AS-IS-модели не означает проверенность требования для стандарта; отсутствие TO-BE-проверок не увеличивает долю проверенного стандарта.
- Отчёт пилота указывает, какие режимы, профили и конструкции проверены, а какие остаются непроверенными.

**Критерий успеха и реестр замечаний:**

- Критерий успеха: прохождение полного цикла без **неразрешённых блокирующих неоднозначностей** (обнаруженные неоднозначности регистрируются) при оценённой приемлемости трудоёмкости.
- Реестр замечаний пилота: предложения по улучшению и выявленные неоднозначности накапливаются в реестре замечаний и не вносятся в структуру до завершения пилота, кроме случаев существенного противоречия, изменения обязательных внешних требований или решения утверждающего органа.

**Переходный период:**

- Длительность переходного периода и поэтапный график расширения области применения. [Заполняется]

- Ограничения переходного периода: что не допускается откладывать до конца периода (например, маркировка ИОД, паспорт модели).

| Код | Модальность | Ключевое слово |
|---|---|---|
| `required` | предписание | «должен», «обязательно» |

| `allowed` | разрешение | «допускается» |

**Различение объектов проверки:** записи соответствия требованиям стандарта и свидетельства — разные объекты. Свидетельства ведутся по приложению Г и связываются с **объектом подтверждения**: утверждением, бизнес-правилом, элементом модели, процедурой или фактом выполнения организационного требования. Помимо бизнес-правил свидетельствами являются, например: протокол утверждения, результат проверки обязательных метаданных, отчёт о целостности идентификаторов, манифест выпуска, результат сравнения экспорта с моделью. Записи проверки соответствия (ниже) ссылаются на свидетельства при необходимости.

**Иллюстративная запись требования.** Идентификаторы, номера пунктов и связи не подтверждают фактической трассировки к исходным требованиям; реальные значения присваиваются при наполнении.

```yaml
schema_version: 1
id: LDM-017
revision: 2                      # редакция требования (3.9)
formulation: >-
  Каждый атрибут согласованного охвата имеет домен из каталога (прил. Е)
  либо локальный домен с обоснованием.
modality: required
applies_to:                      # критерии применимости из 3.5
  level: [LDM]
  profile: [relational, integration, analytical]
  mode: [to-be, as-is]           # состояние фрагмента; о смешанном режиме — семантика ниже
  stage: [5]                     # этап по классификатору 4.2 (5 — «Разработка ЛМД»); семантика — ниже
conditions: []                   # условия, не выражаемые осями (например, «при наличии исторических сущностей»)
exception_allowed: true          # связь с 3.8
verify:
  kind: structural               # вид проверки из 10.1
  criterion: "…"                 # критерий выполнения
  procedure: PR-009              # контрольная процедура (прил. Ж)
  evidence: [паспорт модели, каталог доменов]   # ожидаемые ТИПЫ свидетельств; конкретные ссылки — в записях проверки
sources:                         # перенос из исходных документов (прил. Ф); не нормативное основание
  - {doc: "Требования v1.1", clause: "3.4.2"}
based_on: []                     # нормативные основания (1.7)
relations:
  depends_on: [GEN-005]          # типизированные связи
  refines: [CDM-012]
  replaces: null
status: approved                 # draft | approved | withdrawn
```

Принадлежность редакции выпускам стандарта определяется манифестами выпусков (см. ниже), а не полем записи.

**Семантика применимости:**

- отсутствие оси или условия применимости — «применимо ко всем» значениям оси;
- «применимость не определена» — отдельное явное значение, не равнозначное отсутствию; **допускается только для черновой записи** (`status: draft`);
- при подготовке утверждённого выпуска применимость требования определяется обязательно; требование с неопределённой применимостью в утверждённый выпуск не включается;
- если при проверке конкретной модели применимость установить невозможно, вопрос регистрируется (4.8) и разрешается до положительного заключения по соответствующему обязательному требованию;
- различаются: неопределённость правила применимости (устраняется владельцем требования) и недостаточность сведений о проверяемой модели (результат `insufficient`, устраняется при проверке);
- несколько значений одной оси — любое из них (дизъюнкция); несколько осей — одновременное выполнение (конъюнкция);
- пустой список значений оси не используется; условия, не выражаемые перечнем осей, задаются полем `conditions`;
- **ось `stage`** задаёт этап, к завершению которого требование должно быть выполнено; требование сохраняет применимость при последующей проверке, приёмке и сопровождении результата этого этапа, если явно не установлено иное; момент выполнения контрольной процедуры задаётся процедурой (прил. Ж), а не применимостью требования; **нумерация этапов не устанавливает обязательную хронологию** (4.3) — при реализации не следует считать, что больший номер этапа означает завершение всех предыдущих;
- **смешанный режим**: применимость определяется отдельно для AS-IS- и TO-BE-фрагментов по их состоянию (5.7); значение `mixed` у модели не означает неприменимость требований; дополнительно применяются требования к разграничению состояний (3.4) и переходным соответствиям; ось `mode` характеризует состояние фрагмента, а не режим работы в целом.

**Матрица применения требований AS-IS** (в составе регламента AS-IS, 1.8; схема записи хранится в реестре вместе со схемой требований):

- для каждого требования заявленного выпуска стандарта фиксируются: способ применения (`unchanged` — без изменения | `adapted` — адаптировано | `not_applied` — не применяется), ссылка на адаптированное или специальное требование AS-IS (`{id, revision}`; при `unchanged` отсутствует), обоснование различия, критерий проверки в AS-IS;
- типы связей: `applies_as_is` — одинаковое обязательство, один идентификатор в обоих документах; `adapts_for_mode` — различающиеся обязательства, отдельные идентификаторы; `replaces` для режимных связей не применяется;
- специальные требования AS-IS без целевого аналога ведутся в едином реестре с применимостью `mode: [as-is]`;
- матрица не содержит результатов проверки конкретных моделей — записи проверки ведутся отдельно (см. выше);
- выпуск регламента AS-IS ссылается на выпуск стандарта через манифест и действителен только с заявленным выпуском.

**Манифест выпуска стандарта** — утверждается согласованный набор требований и сопутствующих материалов, а не текущее состояние реестра; редакция требования может входить в несколько последовательных выпусков. **Манифест фиксирует версии всех компонентов, влияющих на содержание, применимость, проверку и согласование требований данного выпуска, включая версию схемы реестра** — это обеспечивает воспроизводимость проверки по прошествии времени, даже если управляемые каталоги изменились. Перечень компонентов универсален и не привязан к конкретным приложениям.

```yaml
schema_version: 1
record: standard_release
release: "1.0"
date: "ГГГГ-ММ-ДД"
status: draft                    # draft | approved
includes:
  requirements: [{id: GEN-001, revision: 1}, {id: LDM-017, revision: 2}]
  components:                    # все компоненты, влияющие на данный выпуск
    - {ref: schema, version: "…"}          # версия схемы реестра
    - {ref: "прил. Г", version: "…"}       # минимальные метаданные
    - {ref: "прил. Д", version: "…"}       # правила именования
    - {ref: "прил. В", version: "…"}       # нотация и легенда
    - {ref: "прил. Е", version: "…"}       # каталог семантических классов и доменов
    - {ref: "прил. И", version: "…"}       # классификация ИОД
    - {ref: "прил. К", version: "…"}       # матрица ответственности
    - {ref: "глоссарий", version: "…"}     # глоссарий (2.1)
    - {ref: "прил. Б", version: "…"}       # профили моделирования
    - {ref: "прил. Ж", version: "…"}       # контрольные процедуры
```

**Запись результата проверки соответствия** — хранится отдельно от требования: требование определяет, *как проверять*; запись результата — *что установлено* для конкретной модели.

```yaml
schema_version: 1
record: verification
id: V-000123                     # идентификатор записи (запуска) проверки
requirement: {id: LDM-017, revision: 2}
standard_release: "1.0"          # проверенный набор требований (манифест)
procedure: {id: PR-009, version: 3}
scope: model                     # охват проверки: model | fragment
object: {model: M-042, version: 5}   # проверяемый объект: версия модели либо фрагмент; тестовые копии — из пространства имён тестовых артефактов
result: verified                 # verified | failed | not_applicable | not_checked | insufficient
evidence: [EV-0451, EV-0452]     # ссылки на конкретные свидетельства (прил. Г)
checked_by:
  initiator: "…"                 # инициатор запуска проверки (роль/исполнитель)
  executor: "…"                  # исполнитель; для автоматической процедуры — средство/система
  date: "ГГГГ-ММ-ДД"
exception: null                  # исключение (3.8) при наличии
```

«Не проверено» (`not_checked`) не считается ни выполнением, ни допустимым исключением; «недостаточно сведений» (`insufficient`) требует доопределения. Связь результатов с решением о приёмке — 10.11.

**Правила ведения:** реестр — мастер-источник формулировок (3.11); текст стандарта формируется из реестра либо проходит автоматическую проверку консистентности.

**Итог по базовой структуре v0.8:** структура зафиксирована как двухдокументный комплект — основной стандарт (целевые и общие нормы) и выделяемый при выпуске регламент AS-IS с полной матрицей применения требований (1.8); подготовлена для AS-IS-пилота. Учтены все рецензии v0.2–v0.6: правила пилотирования отделены от текущего плана; восстановление AS-IS может вестись итеративно от технических источников; основания включения элементов не требуют исходных проектных требований; требования формулируются к документированию, а не к предметным фактам; проверочные случаи изолированы в тестовых копиях; итоги пилота оцениваются тремя раздельными заключениями с раздельным учётом покрытия. Замкнут цикл: требование → применимость → объект → процедура → свидетельство → результат → решение → выпуск → сопровождение. Следующий результат работы — **действующий пилотный комплект AS-IS**: план пилота, требования с ID по схеме приложения А (включая пару из 3.10), восстановленные КМД и ЛМД, контрольные процедуры `PR-xxx`, проверочные случаи в тестовых копиях, протокол приёмки и манифест публикации. Критерий успеха — полное прохождение цикла без неразрешённых блокирующих неоднозначностей при оценённой приемлемости трудоёмкости.
